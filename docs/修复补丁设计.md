# 继承人随机姓名缺陷 — 修复补丁设计

目标构建：`eu4.exe` v1.37.5.0 Inca (491d)
SHA256 `9AD3EFE1AF169F40EE577F9DAE5DEBBC87AF6FB8B5450FB345EBF110DC4D771A`
（任何补丁脚本都必须先校验此哈希，不符即拒绝执行）

缺陷：**有符号取模**（`cdq; idiv`）作用于带符号位的 32 位随机值
⇒ 约 50% 概率余数为负 ⇒ 线性权重扫描第一步即 `break` ⇒ 恒返回该组**第一个条目**。

本文件只做**设计**，不含实现。

---

## 1. 修复目标（先把"改什么语义"定死）

**要修的是"取模的符号性"，不是"权重"、不是"随机数生成器"。**

正确的语义应当是：`index = unsigned(rnd) % 组权重和`，
即把 32 位随机值当作**无符号**数取模，得到 `[0, 组权重和)` 的均匀余数。

三种可实现路径（效果等价）：

| 路径 | 做法 | 保留的随机范围 |
|---|---|---|
| P1 | 把 `cdq; idiv` 改为 `xor edx,edx; div` | **完整 32 位**（最忠实） |
| P2 | 除法前把被除数掩为非负（`and`/`btr`） | 31 位 |
| P3 | 在函数入口把随机**参数**掩到安全位宽 | ≤21 位（见 §4 的必要性） |

> **P3 是唯一能"一处改动覆盖一个函数内全部取模点"的路径**，
> 也是唯一能顺带解决 mode 2 溢出（§3）的路径。

## 2. 数据侧修复为何无效（先说清，避免走弯路）

一个自然的想法是改 `common/countries/*.txt` 里 `monarch_names` 的权重，
比如把第一行的 `= 60` 改小，或者干脆删掉第一行。**这完全无效**，理由是：

```c
v11 = rnd % 权重和;            // rnd < 0 ⇒ v11 < 0
for (i = 0; ; ++i) {
    if (条目属于本组) {
        v11 -= 条目权重;       // 减去任意非负数，结果仍 < 0
        if ( v11 < 0 ) break;  // ★ 第一步必然 break
    }
}
return 条目;                   // 恒为第一个匹配条目
```

即使把第一行权重改成 **0**，`v11 -= 0` 仍为负、仍 `break`、仍返回它。
**负余数使"第一个匹配条目"必然命中，与权重取值完全无关。**
所以必须改代码；数据侧改动只能改变"第一个条目是谁"，不能消除偏向。

## 3. 需要修的站点清单（精确字节）

同类缺陷共 **6 处取模**，分布在 **3 个函数**里：

| # | 函数 | 地址 | 原字节 | 指令 | 备注 |
|---|---|---|---|---|---|
| 1 | `WeightedNameList_PickByRandomIndex` mode1 | `0x140DA98C9` | `99 F7 F9` | `cdq; idiv ecx` | 权重表 B 组 |
| 2 | 同上 mode0 | `0x140DA99FC` | `99 F7 F9` | `cdq; idiv ecx` | 权重表 A 组 |
| 3 | 同上 mode2 | `0x140DA9998` + `0x140DA999D` | `99` … `F7 F9` | `cdq` … `idiv ecx` | **两处不相邻**；且被除数 `1000*rnd` 已 32 位溢出 |
| 4 | `PickNameFromCultureLists` | `0x140280276` | `99 41 F7 F8` | `cdq; idiv r8d` | 文化名回退；**负余数会走越界读分支** |
| 5 | `WeightedNameList_GetByModIndex` | `0x140DA9A84` | `99 41 F7 F8` | `cdq; idiv r8d` | 40 字节元素表 |

### 3.1 站点 4 是**内存安全**问题，不只是分布问题

```c
v12 = a3 % v11;                 // edx = 有符号余数（可能为负）
if ( a3 % v11 >= (int)v10 )     // cmp edx,ecx ; jge  —— 负数 ⇒ 不跳转
    return *a5 + 32*(v12 - v10);
else
    return *a4 + 32*v12;        // ★ 走这里；edx 被零扩展 ⇒ 32 * 巨大数 ⇒ 越界指针
```

反汇编印证：
```
14028027a  cmp  edx, ecx
14028027c  jge  short loc_140280289
14028027e  mov  eax, edx        ; 零扩展
140280280  shl  rax, 5          ; 32 * (unsigned)负值 = 巨大正偏移
140280284  add  rax, r9         ; → 数组之外的"std::string"
```
返回的"字符串"是垃圾内存，随后被当名字使用。
**这很可能就是 `logs\setup_error.log` 与 `gamestate.cpp:6203` 里那些乱码名字
（如 `6579 (*j璭qS`）的来源之一** —— 可作为修复后的验证指标之一（见 §7）。

### 3.2 站点 5 的调用方还有空指针风险

`BuildFullName_Impl`（`sub_140313F40`）：
```c
v15 = WeightedNameList_GetByModIndex(a4, a7);
*a9 = *(_BYTE *)(v15 + 36);     // 若 v15 == 0（空表或未命中）⇒ 读地址 0x24 ⇒ 崩溃
```
未做判空。修复时应一并补判空（或在 stub 中把空表返回改为安全值）。

## 4. 就地字节补丁为何不可行（字节预算）

每个取模点的**正确**最小替换都比原指令长：

| 站点 | 原长 | P1（`xor edx,edx; div`） | P2（`btr` 后 `cdq;idiv`） |
|---|---|---|---|
| 1 / 2 | 3 (`99 F7 F9`) | `31 D2 F7 F1` = 4 → **+1** | 需在别处插 4 字节 → **+4** |
| 3 | `99` 与 `F7 F9` 分离 | 无法就地替换（中间隔着 `mov r9,[r10+18h]`） | 需 trampoline |
| 4 / 5 | 4 (`99 41 F7 F8`) | `31 D2 41 F7 F0` = 5 → **+1** | **+4** |

而且站点 1/2 之后紧接 `4D 2B C3`（`sub r8,r11`），**没有可牺牲的填充字节**；
函数尾部的 `cc` 对齐填充也不足以覆盖全部站点。

**结论：任何就地补丁都必须引入 trampoline / 新增 PE 节 / 注入 DLL，
无法用"等长字节替换"完成。** 这一点决定了架构选择。

## 5. 架构方案对比

> ⚠️ **本节已被 §12 取代。** 调研 EU4DLL 后确认：`plugins\` 目录本身就是一个
> 自动加载点，无需自建代理 DLL。请直接看 §12 的架构定案。

### 方案 A：注入式（原推荐，现已无必要）

写一个 x64 DLL，在 `DllMain` 中按构建哈希校验后 `VirtualProtect` 改写上述字节
（或用 inline hook 直接替换取模逻辑）。

**注入点推荐：`d3d9.dll`**，理由：

| 条件 | 说明 |
|---|---|
| 被静态导入 | `eu4.exe` 导入表含 `d3d9.dll` ✔ |
| 不是 KnownDLL | `d3d9` 不在 KnownDLLs（否则会强制走 System32）——**上线前需查注册表确认** |
| 当前文件是废的 | 游戏根现有 `d3d9.dll` 是 **x86**，x64 进程无法加载，实际一直在用 System32 的版本 ⇒ **替换它不会让现状变差** |
| 转发量极小 | 只需转发 2 个导出：`Direct3DCreate9`、`Direct3DCreate9Ex`（用 `LoadLibraryW(L"C:\\Windows\\System32\\d3d9.dll")` 取真身，避免递归） |
| 对验证免疫 | `eu4.exe` 不变，Steam「验证完整性」不会还原（额外文件一般不被删除） |
| 可扩展 | 后续图形/性能类修复也能挂在同一载体上 |

> 备选注入点：`WINMM.dll`、`IMM32.dll`（同样被静态导入且游戏目录下不存在），
> 但都需先确认不在 KnownDLLs 中。
> **不要覆盖 `VERSION.dll`** —— 它已被第三方中文字体补丁（EU4DLL）占用。

**优点**：单点、可开关、可回滚、便于加护栏、对 Steam 验证免疫、将来可继续扩展。
**缺点**：需要写并构建一个 DLL（VS + `vcvars64.bat`）。

### 方案 B：直接改 `eu4.exe` + 新增 PE 节放 stub

- 新增 `.pfix` 节，写 3 个入口 stub；在各站点用 5 字节 `E9 rel32` 跳过去，
  在 stub 里补回被覆盖的指令后 `jmp` 回原处。
- **优点**：单一文件、无注入依赖。
- **缺点**：站点 1/2/3 可用空间不足（3 字节 vs 需要 5 字节），需连带重建 `sub r8,r11`；
  站点 3 的 `cdq`/`idiv` 分离更棘手；**Steam 验证会还原**；改动点多、回归风险高。

### 方案 C：只做最小止血（4 处，不含 mode 2）

- 只修站点 1、2、4、5，mode 2 因需 64 位重写而暂缓。
- 若走 **P3（入口掩码 ≤21 位）**，则 mode 2 的溢出**自动被消除**，无需重写 ——
  这是 P3 相对 P1 的决定性优势。

## 6. 补丁内容设计（推荐方案 = A + P3）

对 3 个函数各加一个**入口 stub**（放在新增节或 DLL 的代码洞里）：

```asm
; ---- stub: WeightedNameList_PickByRandomIndex  (rcx=table, edx=rnd, r8=coefA, r9=coefB, [rsp+..]=mode)
and   edx, 000FFFFFh        ; 81 E2 FF FF 0F 00  → rnd ∈ [0, 2^20)
<重放被覆盖的原指令>
jmp   <返回原函数 +N>

; ---- stub: PickNameFromCultureLists   (随机值在 edi)
and   edi, 000FFFFFh

; ---- stub: WeightedNameList_GetByModIndex        (随机值在 edx)
and   edx, 000FFFFFh
```

**为什么是 20 位**：mode 2 的被除数是 `1000 * rnd`。

- `1000 × 2^20 ≈ 1.05e9 < 2^31 = 2.147e9` ⇒ **不再溢出**（21 位也刚好够，20 位留余量）。
- 余数均匀性：`2^20 / 权重和`。若权重和约 1000，比值约 1000 ⇒ 取模偏差 **< 0.1%**，可忽略。
- 若某个国家的 `monarch_names` 权重和 > 2^20（约 105 万），会退化为"只覆盖权重范围前段"，
  重新出现表头偏向 —— **上线前必须实测权重和的上界**（见 §7 的护栏）。

> 等价的更保守写法：`btr edx, 31`（4 字节，只清符号位，保留 31 位）。
> 但它**不能**解决 mode 2 的 `1000*rnd` 溢出，因此不推荐单独使用。

## 7. 护栏、验证与回滚

### 7.1 护栏（缺一不可）

1. **构建哈希校验**：`SHA256(eu4.exe) == 9AD3EFE1…` 否则不写内存、记录并退出。
2. **原字节校验**：每个站点写入前先读出并比对原始字节，不符则不写（避免版本漂移后乱改）。
3. **权重和上界断言**：首次进入选取器时读取 `table+16`，若 `> 2^20` 则记警告
   （说明掩码位宽需要调整）。
4. **失败即降级**：任何一步失败都**不修改内存**，游戏按原样运行（不引入新崩溃）。
5. **开关**：支持环境变量 / 配置文件关闭，便于 A/B 对比。

### 7.2 验证

| 层次 | 方法 | 预期 |
|---|---|---|
| 字节级 | 补丁后重新读取那 6 处字节，与目标值比对 | 全部一致 |
| 逻辑级 | 反汇编检查 stub 与跳转目标 | 语义等价、无栈不平衡 |
| 统计级 | 反复触发继承人诞生，统计姓名频次 | 第一名占比回落到接近其权重占比 |
| 副作用级 | 检查 `logs\error.log` / `setup_error.log` | §3.1 的乱码名字条目应消失 |
| 回归级 | 读档、开局、若干年 tick | 无崩溃、无校验和异常 |

### 7.3 回滚

- 注入式：删除代理 DLL 即完全还原（游戏目录无残留、`eu4.exe` 未变）。
- exe 式：保留原始 `binaries\eu4.exe`（工作区已有，哈希 `9AD3EFE1…`），
  补丁脚本须支持 `--revert` 并用记录的原字节还原。

## 8. 影响面与风险披露（必须提前告知）

1. **mode 0 / mode 1 下不影响性别，只影响名字**。
   遍历被 `+36` 过滤，返回的条目必然属于 mode 指定的那一组，
   组内所有条目 `+36` 相同 ⇒ `*genderOut = *(命中条目+36)` **恒等于原值**，性别不变。
   **mode 2（两组混合、不按 `+36` 过滤）是唯一例外**：缺陷下负余数取"整表第一个条目"，
   修复后可能命中另一组的条目 ⇒ **该路径下性别可能改变**。
   ⇒ 影响面主要集中在**名字**上；`mode 2` 的可达性需实测确认。
2. **联机校验和会不一致**，无法与未打补丁的玩家同局。
3. **不改变随机数消费次数**：修复只改"如何解释"随机值，不改变调用次数，
   所以**不会**扰动其它系统的随机序列。
4. 站点 4 的越界读修复后，§3.1 那类乱码可能一并消失 —— 属额外收益，但需实测确认。

## 9. 建议实施顺序

1. **先确认注入点**：读注册表 KnownDLLs，确认 `d3d9` 不在其中；
   若在，改用 `WINMM` / `IMM32`。
2. **写最小代理 DLL**（只转发 2 个导出）+ 护栏骨架，先在**不改任何字节**的情况下验证
   "DLL 确实被加载、且 `Direct3DCreate9` 转发正常、游戏能正常进图"。
3. **再开补丁逻辑**，按站点 1→2→4→5→3 的顺序逐个启用，每加一个站点做一次统计验证。
4. **最后处理 mode 2**：若 P3 掩码已覆盖则无需额外工作；否则做 64 位重写。
5. 产出物按既定约定放工作区（`patches/` 定义 + `dist/` 产物 + `deploy.ps1`），由你部署。

## 10. 数据侧实测确认（补丁参数依据）

对 `common/countries/*.txt` 全量扫描（979 个文件）：

| 指标 | 结果 | 对补丁的意义 |
|---|---|---|
| 定义 `monarch_names` 的文件 | **979 / 979** | 覆盖全部国家 |
| 含**负权重**的文件 | **979** | 负权重是常规写法，不是异常 |
| 负权重条目总数 | **6,944** | — |
| 负权重样例 | `"Aleida #0" = -1`、`"Cordula #0" = -1`、`"Millaray #0" = -1` | **全是女性名** |
| 条目数范围 | 8 – 446 | — |
| **权重和范围** | **18 – 2340** | **远低于 2²⁰ = 1,048,576** ⇒ 20 位掩码安全 |
| 取模偏差估计 | 2²⁰ / 2340 ≈ **448** | 偏差 **< 0.23%**，可忽略 |

### 由此确认的语义

**权重符号编码性别：负值 = 女性名，`abs(权重)` 才是权重。**

- `"Ferdinand #0" = 60` → 男名，权重 60
- `"Aleida #0" = -1` → 女名，权重 1（女性名普遍为 1，即组内等概率）

这与 `WeightedNameList_AddEntry` 的实现**完全吻合**：

```c
v23 = (v5 < 0);        // 负值 ⇒ 标志 = 性别 = 1（女）
v22 = abs32(v5);       // 权重 = 绝对值
*(table+16) += v22;    // 全部条目权重和
if (v23) ++*(table+48); else *(table+20) += v22;   // 分组累加
```

⇒ mode 0 = **挑男名**（模数 `+20` = 男名权重和）、mode 1 = **挑女名**
（模数 `+16-+20` = 女名权重和）、mode 2 = 两组混合。全部自洽。

**副作用确认**：站点 4（`PickNameFromCultureLists`）的越界读会产生垃圾名字，
`logs\setup_error.log` / `gamestate.cpp:6203` 里的乱码（如 `6579 (*j璭qS`）
与此形态一致 —— 修复后应作为**可观测的验证指标**复查。注意：文化名是**回退路径**，
只在 `monarch_names` 未命中时使用，而当前缺陷下加权表几乎总能命中（恒中第一个），
所以**这个越界读目前可能很少被触达** —— 修复加权表后回退路径的调用频率会上升，
反而更需要先把站点 4 一并修掉。**两者必须同时修。**

## 12. 架构定案：复用 EU4DLL 的 `plugins\` 加载点（取代 §5）

### 12.1 决定性事实

调研 [matanki-saito/EU4dll](https://github.com/matanki-saito/EU4dll)（MIT）后确认：

1. 游戏根的 `version.dll` **就是 EU4DLL 自己的 x64 代理**
   —— 其内部 PDB 路径为 `D:\a\EU4dll\EU4dll\x64\Release\version.pdb`。
2. 它的 `Initialize()` 做了三件事：转发 17 个 `version` API 到
   `%SystemRoot%\System32\version.dll`、跑自动更新、然后

   ```cpp
   void LoadScripts(const path& folder) {
       for (auto& e : directory_iterator{ folder })
           if (is_regular_file(e.path()) && e.path().extension() == L".dll")
               LoadLibraryW(e.path().c_str());        // ★ 加载 plugins\ 下【所有】.dll
   }
   ```
3. 本地 `version.dll` 二进制中确实含宽串 `plugins`(×1) 与 `autoupdate`(×4)，与源码吻合。
4. x64 版的 `InitAutoUpdate` 失败**只告警、不退出**（d3d9 旧版才是 `exit(-1)`）。
5. `validateProcess()` 校验宿主进程名为 `eu4.exe`，否则只做转发。

### 12.2 结论：**不需要自建代理 DLL**

> **把一个 DLL 放进 `<游戏目录>\plugins\`，它就会被 `version.dll` 自动
> `LoadLibraryW` 进 `eu4.exe` 进程。**

由此得到的架构是**单层**的：

```
eu4.exe 静态导入 VERSION.dll
  └─ <游戏目录>\version.dll            ← EU4DLL 的代理（已存在，不动它）
       ├─ 转发 version API → System32\version.dll
       └─ for each plugins\*.dll: LoadLibraryW
            ├─ plugins\plugin64.dll           ← EU4DLL 的中文字体挂钩（已存在）
            └─ plugins\MonarchNameFix.dll     ← ★ 我们的修复，新增
```

**收益**：

| 项 | 说明 |
|---|---|
| 零代理 | 不用写转发 DLL、不用劫持系统 DLL、不用管 KnownDLLs |
| 零 exe 改动 | `eu4.exe` 字节不变，Steam「验证完整性」不会还原 |
| 零冲突 | 与 EU4DLL 的 `plugin64.dll` 并列加载，互不干扰；`dllautoupdater` 只按名字更新 `Plugin64.dll`，不会碰我们的文件 |
| 回滚 = 删文件 | 只需删除 `plugins\MonarchNameFix.dll` |
| 迭代快 | 修复逻辑独立成 DLL，改它不需重建代理 |

### 12.3 可复用的现成件（同仓库，MIT）

| 文件 | 用途 | 解决我们的什么问题 |
|---|---|---|
| `Plugin64/injector.hpp`（22 KB） | 社区 injector 库：`WriteBytes` / `MakeCALL` / `MakeJMP` / **自动 trampoline（cave）** | **直接解决 §4 的"+1 字节、就地补丁不可行"** —— 用 `MakeJMP`/`MakeCALL` 自动分配 cave 并生成跳板 |
| `Plugin64/byte_pattern.cpp/.h` | 带通配符的**签名扫描** | 比"构建哈希门槛"更好的版本适配：按特征定位代码，再校验命中处字节 |
| `Plugin64/hooking.hpp`（21.5 KB） | 挂钩框架 | 若将来需要 hook 函数而非改字节 |
| `d3d9/dllmain.cpp` | 代理参考实现（已不需要） | 作为"plugins 加载链"的文档证据 |

> `injector.hpp` 与 `byte_pattern` 都是宽松许可的社区代码，vendor 进我们的 DLL 即可。
> 也可选择 fork EU4DLL 直接在自己的模块里用（见 §12.5）。

### 12.4 实现要点与坑

1. **必须用 RVA / 签名定位，不能写死绝对地址。**
   本文件给的都是 VA，换算成 RVA = `VA - 0x140000000`：

   | 站点 | VA | RVA |
   |---|---|---|
   | mode1 | `0x140DA98C9` | `0xDA98C9` |
   | mode0 | `0x140DA99FC` | `0xDA99FC` |
   | mode2 a | `0x140DA9998` | `0xDA9998` |
   | mode2 b | `0x140DA999D` | `0xDA999D` |
   | 文化名 | `0x140280276` | `0x280276` |
   | 表取值 | `0x140DA9A84` | `0xDA9A84` |

   运行时用 `GetModuleHandleW(nullptr)` 取主模块基址，再解析 PE 头取镜像大小，
   在 `.text` 范围内做签名扫描 → `patch_addr = base + RVA`（并校验命中处原字节）。

2. **`DllMain` 处于 loader lock 之下**（我们是被别的 DLL 的 `DllMain` 加载的）。
   `VirtualProtect` + `memcpy` 这类纯内存操作是安全的，但**不要在 `DllMain` 里
   `LoadLibrary` 其它库、创建线程、或做重活**。若要更保险，可在 `DllMain` 里
   只保存基址，改由一个极轻的线程或首次调用点再补丁。

3. **补丁时机**：`version.dll` 的 `DllMain(PROCESS_ATTACH)` 时 `eu4.exe` 的镜像
   已完整映射，`.text` 已可写保护切换，可安全改写。

4. **不要覆盖/修改 `plugin64.dll` 与 `version.dll`**（会被自动更新覆盖或破坏中文显示）。

5. **别忘 §7 的护栏**：写入前校验原字节、失败不写、可开关、权重和上界断言。

6. **补丁语义按 §6**：三处入口把随机参数掩到 20 位（一处修一个函数内全部取模点，
   并顺带消除 mode 2 的 `1000*rnd` 溢出）。

### 12.5 备选：fork EU4DLL 而非自建 DLL

- **做法**：fork 仓库，在 `Plugin64/` 下加一个 `monarch_name_fix.cpp` + 复用其
  `injector.hpp`/`byte_pattern`，编译出修改版 `plugin64.dll`。
- **优点**：注入链、打补丁框架、版本适配、VS 工程全部现成；单文件替换。
- **缺点**：
  - 与上游分叉，将来上游更新需合并；
  - `plugins\autoupdate64.bat` 会覆盖我们的 `Plugin64.dll`
    —— 必须删除它（README 明确说可以删，且 x64 版自动更新失败只告警不退出）；
  - 修复与"中文字体"功能被绑在一起，不用中文的用户也得背这个依赖。
- **结论**：若你本来就长期使用 EU4DLL，这条路最省事；否则 §12.2 的独立 DLL 更干净。
