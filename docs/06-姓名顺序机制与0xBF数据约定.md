# 06 · 姓名顺序机制与 `0xBF` 数据约定

> 目标：`eu4.exe` v1.37.5.0（Inca），`ImageBase 0x140000000`。全部地址为 **RVA**。
> 相关第三方：**双字节补丁 EU4DLL**（`plugins\plugin64.dll`，521,216 字节）。
>
> 本文回答：**"姓前名后"这件事，游戏自己是怎么表达的？谁能改、挂在哪改、覆盖谁？**
>
> ★ 即使你不关心姓名顺序，**§2 的 `0xBF` 约定**和 **§6 的安装层教训**也值得一读 ——
> 前者是**一个 mod 生态里事实上存在、但从未被写进官方文档的数据约定**；
> 后者是**一个"离线校验没拦住、实机才暴露"的经典案例**。

---

## 1. 游戏自己怎么拼姓名

**`CMonarch` 里没有"拼好的全名"**，只有 `name`（`+0x28`）与 `dynasty`（`+0x68`）两个独立字段。
「姓名」是在**取全名时**才拼出来的。

### 1.1 生成期：`BuildFullName_Impl`（`0x313F40`）

```
① 循环：把「名」按空格切段，逐段 StringAppend + 补一个空格
② 解析「姓」—— 三个来源，在此汇合：
     a. [rbp+0x78] 王朝名（size 非 0 就直接用）
     b. [a3+0x50] 名字表，按 [a3+0x68] 取模选一项
     c. 全局表回退 NameList_PickByModuloWithFallback
③ StringAppend(Src, 姓)
④ Src → *out
```

⇒ **出口串恒为「名… 姓」**。

### 1.2 显示期：`CMonarch_GetFullName`（`0xA4B2C0`）

```
out = CMonarch+0x28 的 name 字段
if (name 非空) out += " "
out += " " + (*(CMonarch+0x68))->name        ← 王朝对象 +0x08 = 王朝名
```

⇒ **显示串恒为「name + 空格 + dynasty」**。

### 1.3 ★ 两个关键含义

1. **"顺序"这件事只能在拼合处决定。** 事后改字段是不可能的 ——
   因为字段里本来就只有"名"和"姓"两半，没有顺序。
2. **有两条互不相同的拼合处**（见 §4）：
   - 生成期 `BuildFullName_Impl` —— 顾问 / 外交官 / 将领 / **共和制**统治者；
   - 显示期 `CMonarch_GetFullName` —— **其他政体**统治者 / 继承人 / 配偶。

## 2. ★★ 数据约定：引号内紧跟一个**裸 `0xBF` 字节**

### 2.1 它长什么样

原始字节证据（`mod\Asian Praefectura Universalis\common\countries\Anqing.txt`）：

```
L326: leader_names = {
L327: "¿1g"   # Zhu     hex: 22 bf 10 31 67 22      ← " + BF + 名字字节 + "
L328: "¿4T"   # Wu      hex: 22 bf 10 34 54 22
L333: "¿Ng"   # Li      hex: 22 bf 10 4e 67 22
L334: "¿òS"   # Shi     hex: 22 bf 10 f2 53 22
```

**判据：`"` 之后紧跟 `BF`（即 `22 bf`）即标记。**

### 2.1 ⚠️ 判据必须再收窄一档

**在数据统计（"某文件里有多少个标记"）这个用途上**，判据 `22 bf` 是对的。
但**在运行期判断"这个串里哪一段是姓"时，还需要再收窄**：

> **真标记判据 = `20 BF`（空格紧跟）或【串首】`BF`。**

**为什么**：在 EU4 自己的编码里，`0xBF` **也可以作为字符的第二个字节**出现
（形如 `10 BF 77`）⇒ 按"**任意 `0xBF`**"判断会**大量误报**。

⇒ **`0xBF` 是"哪一段是姓"的唯一可靠信号**（因为 ASCII 名字本身就含空格）；
文化的 `surname_first` 只决定"**要不要交换**"，不负责"哪段是姓"。

### 2.2 ⚠️ 游戏会折叠「空格 + `0xBF`」⇒ 同一个文化有**两种形态**

| 形态 | 串的样子 | 名长 |
|---|---|---|
| **A** | `名 SP 姓(含 BF)` | `size − dsize − 1` |
| **B** | `名 姓(BF 已被剥)` | `size − deff`（**不减 1**） |

**只认形态 A 的实现，会在形态 B 上每次放弃。**

> ★ 本项目的实测症状：`bai` / `miao` / `yi` / `wu` 这几个文化**每次都放弃**；
> 现场 `dlen = 7` ⇒ 输出 18 字节，而按形态 A 算应当是 20。

⇒ **解析「姓」的起点时必须先判断是不是折叠过的**：
`buf[nlen + (folded ? 0 : 1) + k]`。

### 2.2 为什么"裸 `BF`"是安全的

名字是 **UTF-8 中文**，而游戏按 **CP1252 逐字节**读
（这正是"双字节补丁"要解决的问题）。

在**合法的 UTF-8 文本**里，`0xBF` **只可能以续接字节出现**（在字符中间，如 `10 31` 之后）；
**只有开头的裸 `BF` 是人为标记** ⇒ **判据无歧义** ✓

### 2.3 ⚠️ 两个被证伪的假设（避免后人重走）

| 假设 | 结论 |
|---|---|
| 标记是 **`¿` 字符**（U+00BF，UTF-8 编码为 `C2 BF`） | ❌ **证伪**。真约定是**裸 `0xBF` 字节**。`common/` 里 583 个含 `0xBF` 的文件**全是 `ï¿½` = U+FFFD**（UTF-8 替换字符）；`localisation/` 里 68 个含真 `¿` 的**全是西班牙语文本** |
| `common/` 里有 `¿` 标记 | ❌ **证伪**（同上） |

### 2.4 标记用在哪些数据块（用户 mod 实测统计）

| 数据块 | 标记处数 | 喂给谁 | 双字节补丁是否已支持 |
|---|---|---|---|
| **`leader_names`** | **49,357** | **将领 / 顾问 / 外交官** | ❌ **未支持** |
| `dynasty_names`（**culture** 文件） | 2,355 | 王朝名 | ✅ 已支持 |
| `monarch`（history） | 1,344 | `dynasty = "¿…"` 历史君主 | ✅ |
| `heir`（history） | 599 | `dynasty = "¿…"` | ✅ |
| `define_consort` | 32 | 配偶 | ? |
| `female_names`（culture） | 27 | 女性名池 | ❌ |
| `male_names`（culture） | 7 | 男性名池 | ❌ |
| `queen`（history） | 4 | 王后 | ? |
| `define_ruler` | 1 | 统治者 | ✅ |

**两个结论**：

1. **数据侧几乎已经就绪**（`leader_names` 已标 49,357 处），
   缺的是**代码侧在这条路径上的反转**；
2. **`dynasty_names` 是 culture 级**的 ——
   正好对上"未来改 culture 文件加参数即生效"的方向。

### 2.5 标记是"合成时消费"的显示指令（**重要推论**）

双字节补丁生效的**君主**路径，其 `dynasty` 字段**同样保留标记**
（存档里 **37 / 2143** 个君主带标记即证），而**显示正常**
⇒ **显示端不会单独裸显示该字段**。

**由此可判定**：将领的 `dynasty` 字段保留 `¿` 标记（存档可见
`name="öe^ ¿PO PO(g"` 且 `dynasty="¿PO PO(g"`）**同样无害，无需额外处理** ✓

> 若将来实机发现将领 tooltip 出现孤立 `¿`，再回来定位 `CLeader` 的 `dynasty` 字段写入点即可。

## 3. 双字节补丁（EU4DLL）的机制：标记驱动反转

### 3.1 源码依据（x86 旧版，`Plugin/NameOrder.cpp`，对应 issue #98）

```cpp
// name_creation_func_fix_v1283_start
add  esp, 4
cmp  byte ptr [eax+1], 0xBF      // ★ 检查标记
jnz  jmp2
... 用 npos(-1) 调 CString 成员重排 ...
```

源码注释原文：
> `esiをチェックして逆疑問符¿(0xBF)が最初に来ていれば反転させる`
> （检查 `esi`，若倒问号 `¿`(0xBF) 在最前则反转）

### 3.2 x86 / x64 一致（本地实测）

`plugins\plugin64.dll` 里 `cmp byte ptr [reg+1], 0BFh` **命中 7 处**：

| 文件偏移 | RVA | 形态 |
|---|---|---|
| `0x0300A9` | `0x030CA9` | 独立一处 |
| `0x035BAA` / `0x035BE8` / `0x035C26` / `0x035C64` / `0x035CA2` / `0x035CE3` | `0x0367AA–0x0368E3` | **6 处近似复制**（同一模板的 6 个特化） |

每处前后都是**钩子桩**：

```asm
call qword ptr [rip+X]        ; 原调用（经 .fptable 的游戏函数指针）
push qword ptr [rip+Y]
ret                           ; ← 蹦床，等价 jmp
cmp  byte ptr [rax+1], 0BFh   ; ★ 检查返回的字符串
jnz  skip
mov  qword ptr [rsp+20h], -1  ; -1 = npos ⇒ CString 成员调用
xor  r9d, r9d / mov r8, rax / xor edx, edx / mov rcx, r12 / call [rip+Z]
jmp  done
skip: or r9, -1 / xor r8d, r8d / mov rdx, rax / mov rcx, r12 / call …
```

⇒ **x64 版与 x86 版同源：检测 `0xBF` 标记后反转名字两部分。**

### 3.3 ★ 一条方法论级结论：**钩"调用点"，不是钩"函数"**

注意上面这个形态：**每个调用点各挂一个桩**（7 处 = 7 个独立桩），
而不是"在 `StringAppend` 里钩一次"。

**为什么必须这样** —— 因为被调函数是**通用的**：
本项目另外确认了 `String_TransliterateToCp1252`（`0x1705180`）
**被存档名 / 存档读档选择 / 搜索查询 / 文件名校验多处共用**
⇒ **只能按调用点摘，不能挂钩函数本身**。

> ★ 这是本套文档里**最值得带走的一条工程原则**：
> **当一个函数有多个语义不同的调用者时，钩函数 = 改变所有人的行为；钩调用点 = 只改变你要改的那个。**

### 3.4 补丁的全部可配置项（只有 4 个，**无姓名顺序项**）

⚠️ 这些选项名是 **UTF-16 宽串**，**按 ASCII 搜会漏**。

```
ERROR_TEST
LINE_BREAK_BUFFER_WIDTH              ; CJK 断行缓冲宽度
REVERSING_WORDS_BATTLE_OF_AREA       ; ★ "反转词序"（战区显示）⇒ 方向性证明补丁确有词序能力
SEPARATE_CHARACTER_CODE_POINT        ; = 38936 (0x9818「領」) 断行规则
```

实机 `plugins\plugin.ini`：

```ini
[options]
ERROR_TEST=no
;whitespace=32, 領=38936, 屬=23660, 령=47161
SEPARATE_CHARACTER_CODE_POINT=38936
REVERSING_WORDS_BATTLE_OF_AREA=yes
LINE_BREAK_BUFFER_WIDTH=5
```

⇒ **无姓名顺序相关的配置项。**

### 3.5 ❌ 一个被证伪的期待

**关键字字符串没有直接交叉引用。**

| 关键字 | VA | 交叉引用 |
|---|---|---|
| `leader_names` | `0x142076954` | **无** |
| `monarch_names` | `0x142076B5C` | **无** |
| `dynasty_names` | `0x14216F07C` | **无** |
| `ship_names` | `0x1420A0FC4` | 无 |
| `army_names` | `0x1420B93BC` | 无 |
| `fleet_names` | `0x1420B95C4` | 无 |

**6 个关键字全部无交叉引用** ⇒ 关键字不是靠直接指针比较的，而是：

- 注册进**关键字表**后按 **id** 分派
  （`monarch_names` 由 `ParseMonarchNamesKey`(`0x1417068B0`) 经脚本解析器的**跳转表 case 10324** 进入），或
- 字符串位于某个大字符串池中，引用形式为"**池基址 + 偏移**"，IDA 无法解析。

**已试过并排除**：4 字节 RVA 引用（0 处）、8 字节指针引用（0 处）。

## 4. 覆盖面：唯一的两条拼合路径

### 4.1 为什么不用"逐个角色挂钩"

早期方案是找每个角色的拼装点分别挂钩。走到一半发现**必须换思路**：

- 将领的名字**两条路径**都会产生（一条经 `BuildFullName_Impl`，一条**内联拼装**）；
- 顾问 / 外交官 / 共和制统治者 / 叛军首领 … 各自的入口散落在不同 TU；
- **逐个挂 = 永远漏一个。**

### 4.2 ★★ 落点定论：挂在**共享拼装函数的唯一出口**

**`BuildFullName_Impl` 的出口 `0x314349`**（尾部 `pop r15 / pop r14 / pop rbp`）
⇒ **一处覆盖全部生成期路径**。

这就是站点 **P4**。

### 4.3 覆盖面实证（第 7 轮）

**关键证据**：`Envoy_GenerateName`（size `0x1D6`）的字符串引用里同时出现

```
"Debugging NewRepublicName"                       @0x141C429E8
"C:\mnt\gsg\eu4\eu4\eu4\source\envoys.cpp"         @0x141CAC1D8
```

而它的被调者包含 **`GenerateMonarchName`（`0x313D90`）** ✓

⇒ **外交官（`envoy`）的取名走 `envoys.cpp` → `GenerateMonarchName` → `BuildFullName_Impl`**
⇒ **被 P4 覆盖** ✓
⇒ 且同一函数带有 `"Debugging NewRepublicName"`
⇒ **共和制统治者的"共和名"也由它生成，同一条路径，同样被 P4 覆盖** ✓

**`GenerateMonarchName` 的 15 个调用者逐一归属**（P4 的上游清单）：

| 调用者 | 模块归属 | 对应类别 |
|---|---|---|
| `Advisor_Init` | **advisor.cpp** | 顾问 ✓ |
| **`Envoy_GenerateName`** | **envoys.cpp**（`Debugging NewRepublicName`） | **外交官 + 共和制统治者** ✓ |
| `EffectImpl_CreateGeneral` | country.cpp（`create_general`） | 将领 ✓ |
| `Leader_Create` / `sub_14086C1A0` | leader.cpp | 将领 ✓ |
| `sub_140A9D7B0` | rebelfaction.cpp | 叛军首领 ✓ |
| `Country_CreateNewMonarch` / `Country_GenerateRulerName` | country.cpp | 君主 / 继承人 ✓ |
| `sub_1406526B0` | `CreateRandomRulerOrHeir` | 随机君主 / 继承人 ✓ |
| `sub_140760AA0` | gamestate.cpp | 通用 ✓ |
| `sub_14144AD00` | 名字生成包装 | 通用 ✓ |
| `Leader_GenerateName` / `sub_1406B6BA0` / `sub_140E75F90` / `sub_140E76300` | 效果 / 控制台命令 | 将领 ✓ |

`sub_140E75F90` / `sub_140E76300` 引用 `ConsoleCmdImpl.cpp` 且调用 `CLeader_SetName`
与 `sub_140306BD0`(AddLeader) ⇒ **控制台加将领，被 P5 覆盖** ✓

**唯一一条内联路径**：`create_general` 的 `0x140649A87/AA7` **不经** `BuildFullName_Impl`，
但它把结果交给 **`CLeader_SetName`** ⇒ **P5 覆盖** ✓

### 4.4 ★★ 覆盖面反查（第 8 轮）：**不存在第三条拼装路径**

**做法**：把所有"取带标记姓氏"的调用点逐个看其被调者，判断它**是否真的拼装姓名**。

| 函数 | 有无拼接动作 | 结论 |
|---|---|---|
| `sub_1402C2B10` | 无 —— 解析王朝后转交 `Country_CreateHeir_Impl` | 拼装在 P4 |
| `sub_140A56DA0` | 无 —— 仅解析并指派王朝（无 `StringAppend`、无 setter） | 与姓名无关 |
| `Heir_InitNewHeir`（`0xA55CF0`） | 无 —— 只取**名字**并 `StringAssign`（无空格拼接） | 全名拼装在 P4 |
| `sub_140A56F90` | 无 —— 形状与上者相同（配偶 / 王后初始化） | 同上 |
| `CreateRandomRulerOrHeir`（`0x6526B0`） | 走 envoys.cpp 家族 + `GovernmentReformStack_IsRepublicanName` | **共和制统治者第二次确证 ⇒ P4** |

★★ **判据（本轮反查用的硬性筛选条件）**：

> **一个函数若没有 `StringAppend`，它就不可能产出 `"<名>␠¿<姓>"` 这种拼接串**
> —— 因为拼接必然经过 `StringAppend`。

⇒ **结论**：每个真正拼装姓名的路径，要么经过 `BuildFullName_Impl`（P4），
要么终结于 `CLeader_SetName`（P5）。**只取名不拼接的函数不构成第三条路径。**

### 4.6 一处值得记下的"存储层差异"

**顾问与将领的名字在存档里的布局完全相同**（E1，存档实证）。

但**存储层有差异** —— 这正是"补丁对将领无效"的根本原因：
两条路径**写字段的方式不同**，所以在**某一个**落点挂钩对其中一类无效。

⇒ **教训**：**"同一个类"不等于"同一条写入路径"。**
判覆盖面要看**写入点**，不能只看类型。

## 5. ★ 按文化决定顺序（而不是按 `0xBF` 标记）

### 5.1 核心问题

**在姓名合成点，能不能拿到"文化"？**

### 5.2 结论：能，且在 P4 挂钩点上**免费可得**

**证据链（两个独立见证）**

**见证一** —— `PickNameFromCulture`（`0x280340`）：

```c
__int64 PickNameFromCulture(_QWORD *a1, char a2/*性别*/, int a3/*随机*/)
{
    v3 = a1[17];                                  // a1 + 0x88 = 文化对象
    if (a2) return PickNameFromCultureLists(a1, a2, a3, a1 + 25, (v3 + 224));  // 文化 + 0xE0
    else    return PickNameFromCultureLists(a1, 0,  a3, a1 + 22, (v3 + 200));  // 文化 + 0xC8
}
```

**见证二** —— `BuildFullName_Impl`（`0x313F40`）内部：

```asm
0x140313F68  mov r14, r8            ; ★ 第 3 个参数 (r8) → r14
0x1403141A4  mov rax, [r14+88h]     ; ★ 文化对象 = *(第3参数 + 0x88)
0x1403141B0  lea rcx, [rax+0E0h]    ; 男性：文化对象 + 0xE0
0x1403141C9  add rax, 0C8h          ; 女性：文化对象 + 0xC8
0x1403141DD  call PickNameFromCultureLists
```

**两处都从同一偏移（`+0x88`）取对象、再取 `+0xC8`/`+0xE0` 的男女名表**
⇒ **该对象确凿是「文化」**（不是国家、不是宗教）✓

### 5.3 ★ 为什么 P4 挂钩点能直接用它

```
函数序言： push r14
函数尾声： pop r15 ; pop r14 ; pop rbp     ← 正是 P4 覆盖的 5 字节站点
```

**我的桩在这三个 `pop` 执行之前进入** ⇒ **`r14` 仍等于第 3 参数**
⇒ 一条 `mov rax, [r14+88h]` 即得文化对象 ✓✓

### 5.4 落地形态

把 P4 的判据从"检测 `0xBF` 标记"换成
**"查 `*(r14+0x88)` 这个文化是否在配置的名单里"**，
即可实现**按文化一刀切**，且**不需要改变桩的挂点、不需要新的桩** ✓

**配置形态**（`common\cultures_name\*.txt`）：

```
# 姓前名后的文化。
#   surname_first = yes|no     默认 yes（写了这个块就表示要姓前名后）
#   separator     = "..."      姓与名之间的拼接符；"" 表示不加空格，" " 表示加一个空格

chihan = { surname_first = yes  separator = ""  }
mongol = { surname_first = yes  separator = " " }
```

也接受不带大括号的写法（`cantonese = surname_first = yes separator = ""`）。
文化名 = `common\cultures\*.txt` 里的**脚本名**。

**加载顺序**（后读的覆盖先读的，模组覆盖基础游戏）：

```
1. <游戏根>\common\cultures_name\*.txt
2. 用户目录下 dlc_load.json 的 enabled_mods → 各 .mod 的 path= → <path>\common\cultures_name\*.txt
```

### 5.5 遗留问题：P5 拿不到文化

**P5（`CLeader_SetName` 入口）拿不到文化** —— 它的入参只有 `this` 与姓名字符串。

但将领名有**两条**路径：

- 经 `BuildFullName_Impl` 的走 **P4** ✓；
- **内联拼装**那条（`create_general` 的 `0x140649A87/AA7`）需另找文化来源。
  可行落点：该路径上 `PickNameFromCulture` 的调用点 **`0x140649997`**，
  其 `rcx` 即承载文化的结构（**同样按 `+0x88` 取**）✓

**顾问 / 外交官（envoy 的四类）**：names 全走 `GenerateMonarchName` → `BuildFullName_Impl`
⇒ **只需 P4** ✓

## 6. ★★ 安装层教训：离线校验没拦住、实机才暴露

**这是本文最值钱的一节。**

### 6.1 实机日志

```
[i] ready P1 … site=0xda989b     [i] ready P2 … site=0x280274     [i] ready P3 … site=0xda9a82
[!] original bytes mismatch: P4 BuildFullName_Impl exit (name order)
[!] original bytes mismatch: P5 CLeader::SetName entry (name order)
[i] result: 3/5 patches applied
```

**两个缺陷，都在"补丁表 / 安装逻辑"里，不在桩、也不在变换逻辑里。**

### 6.2 缺陷 ①：护栏把"通配"当成"不匹配"

```c
for (i = 0; i < 5; i++)
    if (!s.mask[i] || site[i] != s.bytes[i]) { 失败 }   // ← 错
```

`!s.mask[i]` 的意思是"该字节是 `??` **通配**"，
却**直接判失败** ⇒ **签名里只要带通配就必然不通过**。

P1–P3 的签名前 5 字节恰好全是具体值，所以**侥幸成功**；
P4/P5 的签名第 5 字节是 `??` ⇒ **必失败**。

### 6.3 缺陷 ②：`site` 取的是"签名命中处"，而 P4 的站点不在那里

```c
site = (uint8_t *)hit;   // hit = 签名命中处 = BuildFullName_Impl 开头 0x00313F40
```

P4 要打的站点是**函数唯一出口 `0x00314349`**（尾部 3 个 `pop`）。
`rva` 字段被用作"签名命中处的交叉校验值"，于是站点被当成函数开头
⇒ **即使护栏放行，P4 也会去改写函数序言 —— 后果严重。**

### 6.4 修法：把三个概念拆开

| 字段 | 含义 |
|---|---|
| `rva` | **签名命中处**的预期 RVA（交叉校验"是不是同一个函数"） |
| **`site_rva`** | **真正打补丁的站点** RVA（P1–P3 与 `rva` 相同；**P4 不同**） |
| **`site_bytes`** | **站点原字节**（hex + `??` 通配），护栏**按它**逐字节校验 |

### 6.5 为什么离线没拦住 —— 校验器的升级

此前 `verify_nameorder_target.py` 只**手工**查了 P4 一个站点的字节，
**没有校验"安装逻辑"**。

现改为**从 `monarchnamefix.c` 解析整张补丁表**，逐条对 `eu4.exe` 校验：

- 签名命中 RVA
- `site_rva` 处原字节
- **回跳点位置**（出口型站点须为 `C3`）
- `cover >= 5`

```
P1 … 0xda989b  0xda989b  OK      P4 … 0x313f40  0x314349  OK
P2 … 0x280274  0x280274  OK      P5 … 0x861fc0  0x861fc0  OK
P3 … 0xda9a82  0xda9a82  OK
[PASS] 补丁表全部条目通过静态校验
```

### 6.6 ★ 教训

> **桩的机器码我逐一字节核对、还用真实执行测了，却漏掉"桩挂到哪"这一层。**

⇒ **以后新增补丁点，必须让校验器覆盖"签名命中处 / 站点 / 回跳点"三者的关系**，
而不是只验桩、或只验单个站点字节。

### 6.7 另一条同类教训：抽出公共实现时必须**同时删除旧副本**

`nameordertest.c` 是第 2 轮写的，内含**自己的 `patch_name_order` 实现**；
第 4 轮抽出 `nameorder.h` 时**忘了删它**
⇒ 改分隔符后 **DLL 生效、而该测试仍测旧逻辑**（表现为 6 例失败）。

> **这恰是 `nameorder.h` 本要防止的"实现分叉"。**

**更糟的是**：它这次给出的是**虚假的失败** ——
若据此去"修"正确的 DLL 代码，就会**把好的改坏**。

## 7. 分隔符的三种语义（配置层）

| 配置 | 行为 |
|---|---|
| `separator = " "` | 姓 名（中间一个空格） |
| `separator = ""` | 姓名（直接相连，不加任何字符） |
| **未写 `separator`** | 用**全局缺省** |
| `surname_first = no` | 完全不介入 |

> ⚠️ **`separator` 的缺省值曾经在本项目文档里写反过。**
> 代码里的全局缺省 `NAME_ORDER_SEP` 是 **`""`（连写）**，
> 与"不写 `surname_first` 时默认 `yes`"是同一套"**写块即为中式姓名**"的思路。

**名字内部原有的空格不受影响**（`"Jean Claude"` 仍带空格）。

### 7.1 一个正面副作用

因为变换在 P4 处（`BuildFullName_Impl` 出口）**比双字节补丁的调用点钩子更早执行**，
**君主的名字现在也由本补丁统一处理** ⇒ 分隔符改动对统治者同样生效 ✓
