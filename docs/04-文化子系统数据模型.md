# 04 · EU4 文化（Culture）子系统数据模型

> 目标：`eu4.exe` v1.37.5.0（Inca），`ImageBase 0x140000000`。全部地址为 **RVA**。
> 本文是文化子系统的**权威参考**：三个类 + 一个记录容器、加载全链、名字表机制、键名池。
>
> ⚠️ **先读 §3.5「判类型」** —— 本子系统在头 4 轮里**归属判错了 3 次**，
> 三次都是同一个错误：**没先确认自己在哪个类上**。

---

## 1. 一句话全貌

```
【脚本层】 common/cultures/*.txt
   ↓  CultureDatabase::Load("/cultures")   → 枚举 *.txt，逐文件解析
【解析层】 CultureFile_ParseAll (0x27BC00)

【取名层】 Country_ResolveMonarchNameTable / PickNameFromCultureLists
```

## 2. 三个类（+ 一个磁盘记录容器）

| # | 类 | vtable | 大小 | 构造 / 删除析构 | 备注 |
|---|---|---|---|---|---|
| **①** | **`Culture`**（运行期文化对象） | **`0x141C4F070`**（全库 **1 处**引用） | **`0x3E0` = 992** | `0x27E810` / `0x27EAC0` | 见 §3 |
| **②** | **`CultureGroup`** : `Culture` | **`0x141C4F028`** | 同 ①（**无新增字段**） | `0x2805E0`（从宿主链表摘除） | 槽 9 = `sub_14027EAC0`（① 的删除析构）⇒ **派生确证**；槽 8 = **恒假桩** |
| **③** | **`磁盘记录`**（每个 `cultures/*.txt` 一条） | **`0x141C4F108`**（变体 `0x141C4F0C0`） | `new(0x3E8)` = 1000 | `0x27C9F0` / `0x27CE40` | 槽 4 = `sub_14027CF20` |

### 2.1 两个默认对象（惰性单例）

```c
// sub_140280520 → qword_14233D8C8
v = new(0x3E8); sub_14027C9F0(v, "noculturegroup", 0); *v = off_141C4F0C0;

// sub_1402806A0 → qword_14233D8C0
v = new(0x3E0); sub_14027E810(v, qword_14233D8C8, "noculture"); *v = off_141C4F028;
```

| 全局槽 | 名字 | 大小 | 创建者 |
|---|---|---|---|
| `qword_14233D8C8` | **`"noculturegroup"`** | `new(0x3E8)` | `sub_140280520` |
| `qword_14233D8C0` | **`"noculture"`** | `new(0x3E0)` | `sub_1402806A0`（`+0x88` = 组单例） |

**★ 三条推论**：

1. **`0x141C4F108` 与 `0x141C4F0C0` 是同一类的两个 vtable 变体**（逐槽相同），**不是两个类**；
2. `qword_14233D8C8` = `"noculturegroup"`（1000 B）—— 就是 `Load` 里**当第 1 条记录插入库**的那个；
3. `qword_14233D8C0` = `"noculture"`（992 B）—— 就是 `CultureDb_FindByName` **未命中时的返回值**（"未知文化"哨兵）。

### 2.2 持有关系：**父 `Culture` 持有子 `Culture` 链表**

> ⚠️ **本项目第 19 轮的一处归属更正，务必按新版理解。**

**早前的写法**是"一个文件 → 一个记录 → **它持有该文件全部 `Culture`**"，
即把链表归给了**③ 磁盘记录**。

**更正后的结论**：`sub_14027CF20` 的 **`this` 就是 `Culture`**（②），不是记录 ——
证据是 `0x14027D2F0 mov rdx, r15`：这条把 **`this` 当作 `groupId`** 传给子 `Culture` 的构造器。
而该对象**自带 `+0xC8` / `+0xE0` 两张名表**，只有 `Culture` 才有。

⇒ 正确的模型是：

```
② Culture（父）
    +0x10  子链表【首节点】别名
    +0x18  子链表头
    +0x20  子链表计数（u32）
        └─ 节点 new(0x20) { obj@+0, prev@+8, next@+0x10, flag@+0x18 }
              └─ 每个节点装一个 new(0x3E0) + sub_14027E810 造出的子 Culture
```

而 **③ 磁盘记录**只是"**文件级 / 记录级**容器"，
**它不是 `sub_14027CF20` 的 `this`**。

**★ 一处引擎细节**：销毁路径对 `+0x10` 的写是 `and rax, -8 / or rax, 1`
⇒ **链表指针的低 3 位被当标志位用**。

### 2.3 两条独立的通路（最容易混的一点）

| 通路 | 容器 | 里面放的是 |
|---|---|---|
| **A** | `CultureDatabase`（`qword_14242BA98`）的数组 / 哈希 | **③ 磁盘记录** |
| **B** | `qword_14233D8D0[+0x118][id]` | **① `Culture`** |

⇒ ★ **读到名字的 `+0x48` 之前，必须先知道自己在 A 还是 B 上**。

### 3.3 ⚠️ 一个必须解释的矛盾：`sub_14027EB80` 到底属于谁

**第 4 轮时发现**：`sub_14027EB80` 访问 **`[r14+0x444]`**，
而 `Culture` 只有 **`0x3E0`** 字节 ⇒ **它不可能是 `Culture` 的字段读取器**。

**第 5–6 轮清账结论**：

| 事实 | 值 |
|---|---|
| `sub_14027EB80` 的签名 | `rcx` = 目标对象（`r15`）/ `rdx` = **解析上下文**（`r14`）/ `r8d` = 键 id |
| 键 id 链 | `0x2843 · 0x2CE4 · 0x5A · 0x52 · 0x223`，用 `sub r8d, imm` 分发 |

⇒ ★ **`[r14+0x444]` 的基址是「上下文」，不是目标对象** —— 矛盾消解 ✓
⇒ 但它**确实同时挂在 `Culture` 和 `CultureGroup` 的槽 4 上**（同类）。

**类归属清账硬数据**：

| vtable | 类 | 槽 4（`+0x20`） | 写入者（构造器） |
|---|---|---|---|
| `0x141C4F070` | **`Culture`**（`0x3E0`） | `sub_14027EB80` | `sub_14027E810` |
| `0x141C4F028` | **`CultureGroup`**（同族） | `sub_14027EB80`（**同槽**） | `sub_1402805E0` / `sub_1402806A0` |
| `0x141C4F108` | **磁盘记录** | `sub_14027CF20` | `sub_14027C9F0` |

> ⚠️ **一处记法更正**：vtable **槽 4 的字节偏移是 `0x20`**（两个 qword 之后）。
> 项目里曾把它误记成"槽 2"。

### 3.5 ★★★ 判类型：vtable → 首参 → 对象大小（**缺一必错**）

> **本子系统头 4 轮里错了 3 次**，全部是同一个错误。

**强制判据**：

1. `lea rax, off_XXXX` **认 vtable** → 确定是哪个类；
2. 确认函数**第一个参数是哪个类的实例**；
3. 用**对象大小**交叉检验（**能访问 `+0x444` 的对象一定 > `0x3E0`**）；
4. **才看字段偏移**。

**跳过 ①③ 必错。**

**三个真实踩坑记录**：

| # | 错误 | 更正 |
|---|---|---|
| 1 | 据 `FindByName` 的 `lea rcx,[rsi+48h]` 说"名字在 `+0x48`"，又据记录构造器"更正"为 `+0x38` | ★ **两个结论各自在自己那层都对**（③ 记录名在 `+0x38`；① 文化名在 `+0x48`）。错的只是**没先确认自己在哪个类型上** |
| 2 | 据删除析构里的 `0x3E8` 判"记录 = 1000 字节" | ⚠️ **`0x3E8` 是引擎里 220 处通用分配** ⇒ **判类型要用 vtable 引用 + 分配点上下文，别用裸常量** |
| 3 | 把 `+0x1110` / `+0x1170` 只记成"文化字段" | ⚠️ **`Country_Resolve*` 返回的是"当前对象"**（可能是变体文化、**也可能是国家自己**），随后才 `add rdx/rcx, 1110h/1170h` ⇒ **读表的人有两个，国家是其中之一** |
| 4 | 以为 `sub_1408EB880(a1, name)` 是"列表头初始化" | 实际是**在 `a1` 就地构造一个 ≥`0x160` 的子对象**（写 `a1+0x18` 名字文本、`a1+0x158` 键串；其它调用点分配 `0x2A8`/`0x270`/`0x2E0`）⇒ 文化构造器里的 `+0xE0` / `+0x258` 是**子对象嵌入位**，不是"名字表头" |

> ⇒ ★ **教训：同一个 `culture.cpp` 里有多个类，动手前先 `lea rax, off_XXXX` 定位类型。**

### 4.2 `CultureFile_ParseAll`（`0x27BC00`）

★ **归属确证**：它是内部源码路径 `…\source\culture.cpp` + `"Culture Group #"` 的**唯一引用者**。

```

· 名字在 tok+0x34

· 未命中 ⇒ new(0x3E8) + 记录构造
```

> ★ **"记录的 Read"是两段式**：

### 4.3 ★★ 哈希：与补丁**不是同一套**

```c
h = 0;
while (*s) h = 61 * (h + (signed char)*s), ++s;    // ★ 有符号字符，61 进制
桶 = h % 511                                        // ★ 无符号 div
```

- **桶数 = 511**（`0x1FF`）；
- 桶表 `new(0xFF8)`（= 511 × 8）；
- 节点 `new(0x10)`；
- **未命中返回哨兵 `qword_14233D8C0`**（= `"noculture"`）。

> ★ **注意"61"**：这是一个**独立于名字池哈希**的算法。
> ⚠️ 本子系统里出现过**两套哈希**（文化库哈希 vs 图形文化库的按名查询），别混。

### 4.4 `CultureDatabase` 布局（`new(0x40)`）

## 5. ★★★ 名字表机制（本子系统的核心结论）

### 5.1 脚本侧

```
male_names   = { NAME = { "Erik" "Lars" } }      ← 键名池 0x1421C14BC
female_names = { … }                             ← 键名池 0x1421C16C4
```

### 5.2 解析侧（字段读取器 `sub_14027CF20` 对两个列表**逐指令同构**处理）

```asm
14027D6B9  mov  rbx, [rbp+arg_0]      ; 记录
14027D6C0  add  rbx, 0E0h             ; 女名表（另一处 14027DCA0: add rbx,0C8h = 男名表）
14027D6CA  lea  rdx,"NAME" / call strncmp    ; ★ 脚本键 = NAME
14027D6F6  call LookupLocalizedString        ; 每个值先本地化
14027D6FF  mov  rdx,[rbx+8] / cmp rdx,[rbx+10h]   ; 列表 = {alloc@+0, begin@+8, end@+0x10}
14027D730  add qword [rbx+8], 20h             ; ★★ 元素 0x20 ⇒ 元素就是 CString
```

**⇒ 名字表 = 32 字节 `CString` 的 `std::vector`。**

### 5.3 ★★★ 三方吻合（三条独立证据指向同一结构）

| 证据来源 | 说明 |
|---|---|
| `StringArrayDestroy`（`0x140094E60`） | `{begin,end,cap}` 的 `CString` **数组**析构：每 32 字节一个元素逐个 `StringFree` |
| `PickNameFromCultureLists` 的 **`>>5`** | 元素数 = `(end − begin) >> 5` ⇒ **元素 32 字节** |
| 本目录的机器码 | `add qword [rbx+8], 20h` ⇒ **步进 0x20** |

### 5.4 ★★ 一条最容易搞错的区分

> **`strncmp(条目名, "NAME", …)` 里的 `"NAME"`（大写字面量）**
> **与键名池里的 `male_names` / `female_names` 不是同一个串。**

- **`"NAME"`** = **块内条目名**（`male_names = { NAME = { … } }` 里的 `NAME`）；
- **`male_names`** = **块本身的键**。

同理 `culture_record_construct.cpp` 里的 `"noculturegroup"` / `"westerngfx"` 也是**字面量**
（有 xref 可查，**与池内名字的"无 xref"形成对照**）。

### 5.5 ⚠️ 一处曾经的误判（第 18 轮更正）

`0xC8` / `0xE0` 这两处分支**不是"外层键选表"**，
而是"**把 `hdr+0x18` 按 `\n` 切分**"的循环出口（`hdr = ctx+0x28`），
且 `0xC8` / `0xE0` 在**全函数各只出现一次**
⇒ **外层键的分派点不在本函数**。

**已排除三处**：

| 位置 | 结果 |
|---|---|
| 字段读取器 `sub_14027CF20` 内部 | `0xC8`/`0xE0` 各 1 次，且是 `\n` 切分出口 |
| 解析主循环 `sub_14027BC00` | **0 命中** |
| `ParseScriptFields` | **0 命中** —— 已确证它**只负责转交**（`GetCurrentKey(ctx)` → 读 `ctx+0x30` → `call [vtable+0x20]`） |

⇒ **仍未定位**（见 §8）。

## 6. 键名池（interned）

脚本键名放在 `0x142xxxxx`，**无 xref**，只能按 **id** 间接寻址
（引擎把键 intern 成序号 id，存于**解析上下文 `+0x30`**）。

| 字段名 | 地址 | 语义 | 证据 |
|---|---|---|---|
| **`male_names`** | `0x1421C14BC` | 男名表 → `文化+0xC8` | `sub_14027CF20@0x14027DCA0 add rbx,0C8h` |
| **`female_names`** | `0x1421C16C4` | 女名表 → `文化+0xE0` | `@0x14027D6C0 add rbx,0E0h` |
| **`dynasty_names`** | `0x14216F07C` | 王朝名数组（元素 32 B） | `Country_ResolveDynastyNameList` |
| **`monarch_names`** | `0x142076B5C` | 君主名**加权表**（元素 40 B） | `Country_ResolveMonarchNameTable` → `+0x1170` |
| **`graphical_culture`** | `0x14208A42C` | 图形文化：按名查**图形文化库** | `culture_record_construct.cpp@0x14027CC82` |

**与文化相关的其它已定位名字**：

| 名字 | 地址 |
|---|---|
| `IS_PRIMARY_CULTURE` | `0x141D0B2C0` |
| `ACCEPTED_CULTURE` | `0x141CD7790` |
| `CULTURE_GROUP` | `0x141CB23B0` |
| `accepted_culture` / `culture_group` | `0x141D410D0` / `0x1420A07A4` |

### 6.1 池的形态（raw 抽样）

每个名字前带**非字符串头字节**，名字之间有**未使用空隙**：

```
0x1421C14B8 : '.1'          ← 前一条的名字（头字节 0x00 在前）
0x1421C14BC : 'male_names'  ← 前 1 字节 = 0x00
0x1421C16C0 : '/1'
0x1421C16C4 : 'female_names'
```

### 6.2 id ↔ 名字的连接：**仍未打通**

字段读取器 `sub_14027CF20` 按**数字键 id** 分派，已读出的 4 个键：

| 键 id | 分支写入 | 备注 |
|---|---|---|
| `0x52`（82） | 记录 `+0x28` | 经图形文化库按名查（键名取自 `ctx+0x444`） |
| `0x5A`（90） | 操作 `+0xF8` 子对象 | 连调虚槽 3 与虚槽 16 |
| `0x2843`（10307） | 操作 `+0x270` 子对象 | 与上者同构 |
| `0x2B12`（11026） | 记录 `+0x30` | 同查库路径 |

**要把 id ↔ 名字对上，只差最后一步**：找到**按 id 取键名**的那个函数
（池既无指针表也无直接引用 ⇒ 必是"**基址 + id**"寻址）。

> ★ **§6 表里的 5 个地址就是为这一步准备的校验锚点**：
> 一旦找到该函数，用它取 `id` 处的名字，与上表地址比对即可**立刻确认**。

**复现方法**：

```python
# IDA: 全库字符串正则找字段名
find_regex(r"^(male_names|female_names|dynasty_names|monarch_names|graphical_culture)$")
# ⇒ 5 处，地址见 §6

# 逐个查 xref（预期：全部 0 处）
xrefs_to(0x1421C14BC)  # male_names
```
