# 05 · 陷阱：`std::string` 的 SSO 分界（15 字符）

> 目标：`eu4.exe` v1.37.5.0（Inca），`ImageBase 0x140000000`。
> 本文讲一个**改内存补丁时人人都可能踩、且症状极具误导性**的坑。
>
> 症状：**同一个函数、同一段代码，对大多数文化正确，对少数文化读到乱码。**
> 根因：字符串的**存储位置随长度改变**。

---

## 1. 一句话

**`std::string` 在短串时把字符数据内联在对象里，长串时改存堆指针。**

引擎全程用同一个判据：

```c
capacity < 0x10   ⇒  数据【内联】在字符串对象起始处
capacity >= 0x10  ⇒  对象起始处的 8 字节是【堆指针】
```

⇒ **任何把字符串字段当裸 `char*` 读的代码，只对短串有效。**

阈值是 **15 个字符**（SSO 缓冲 16 字节，含结尾 `\0`）。
第 **16** 个字符正好跨过它。

---

## 2. 现场：`shandong_culture` 为什么读不出来

### 2.1 症状

配置文件里明明有 `shandong_culture`，日志里 `CFGENTRY #13 "shandong_culture"` 也打印出来了
（说明**配置解析没问题**），但**整份日志里从未出现该文化的生成记录或显示记录**。

**并且**：显示期的诊断行打出的是**非 ASCII 垃圾**，且"同一串字节、涉及多个国家"
（ENG / FRA / SDF / SDG 等多个 tag 都读到同一串）。

> ★ 最后那句是**决定性的线索**：不同国家读到**同一串字节**，
> 说明那不是"名字"，而是**同一个指针值**被当字符读了。

### 2.2 根因

文化名是 `std::string`（32 字节：`+0x00` 数据/SSO 联合 · `+0x10` size · `+0x18` cap）。
要读的字段在**文化对象 `+0x48`**。

| 文化名 | 字符数 | SSO？ | **`文化对象 + 0x48` 实际是什么** | 把 `+0x48` 当 `char*` 裸读的结果 |
|---|---|---|---|---|
| `swedish` | **7** | ✅ SSO（cap=15） | **字符 `"swedish"` 本身**（`+0x48` 后紧跟 `\0`） | ✅ **正确** —— 这就是它一直"看起来对"的原因 |
| `shandong_culture` | **16** | ❌ 堆（cap≥16） | **堆指针的 8 个字节** | ❌ **指针字节** ⇒ 非 ASCII 垃圾，且**随 ASLR 变** |

★ **`shandong_culture` 恰好第 16 个字符** ⇒ 正好跨过 SSO 阈值。
★ **为什么短名"看起来就是名字"**：`+0x48` 是字符串对象的**数据字段**，
SSO 时它本身就装着字符 ⇒ 裸读碰巧正确。**这是最危险的一类 bug：测试用例全过。**

### 2.3 因果链（为什么"整份日志从未出现"）

| 步骤 | 位置 | 结论 |
|---|---|---|
| ① 文化名的**唯一**写入点 | 生成期入口的捕获函数（从 `a3+0x48` 裸读） | ⇒ **长名写不进去** |
| ② 候选名的**唯一**来源 | 用 ① 的结果去查配置表 | 长名 ⇒ 名字无效 ⇒ **根本不查配置** |
| ③ 按名字匹配本身**是健康的** | 配置侧读 `+0x120` 时**带了 SSO 判据** | ⇒ 失败**不在匹配**，而在**候选名没拿到** |
| ④ 现象 | "整份日志从未出现 `shandong_culture`" | **完全自洽**：它不进任何取名函数，是因为**它的名字从没被正确捕获过** |

⇒ **同一个补丁里，一处写对了（带 SSO 判据）、两处写错了（裸读）** ——
所以这不是"认知缺失"，而是**捕获路径漏了这一步**。

## 3. 正确读法（照抄引擎，不要自创）

引擎自己的读法（在文化子系统的多个函数里都实测到 `cmp [x+18h],10h` 这类判据）：

```c
/* obj = 文化对象；名字字段起始 +0x48 */
const uint32_t NAME_OFF  = 0x48;
const uint32_t NAME_SIZE = 0x48 + 0x10;   /* size @ 对象+0x10 */
const uint32_t NAME_CAP  = 0x48 + 0x18;   /* cap  @ 对象+0x18 */

uint64_t cap = 0, sz = 0, data = 0;
if (!read_bytes((const uint8_t *)obj + NAME_CAP,  &cap,  8)) return;
if (!read_bytes((const uint8_t *)obj + NAME_SIZE, &sz,   8)) return;
if (!read_bytes((const uint8_t *)obj + NAME_OFF,  &data, 8)) return;

if (cap < 0x10)                                    /* ★ SSO 判据 */
    data = (uint64_t)(uintptr_t)((const uint8_t *)obj + NAME_OFF);

if (!data || sz == 0 || sz > 128) return;          /* 合理性 + 上限 */
if (!region_ok(NULL, (const uint8_t *)(uintptr_t)data, (size_t)sz + 1)) return;
if (!read_bytes((const uint8_t *)(uintptr_t)data, buf, (size_t)sz + 1)) return;

name = buf;   /* 之后走原有校验 */
```

**★ 通用形式**（任意 `CString` 字段）：

```c
/* field_off = 字段起始偏移（= 对象 + field_off 处是 data/SSO 联合） */
cap  = *(uint64_t *)(obj + field_off + 0x18);
sz   = *(uint64_t *)(obj + field_off + 0x10);
data = (cap < 0x10) ? (obj + field_off) : *(const char **)(obj + field_off);
```

### 3.1 三条附带建议

1. **字段上限要设**：`CULT_NAME_MAX = 64` **已核实足够** ✓（不是截断问题）。
2. **ASCII 校验保留**：`if (c < 0x20 || c >= 0x7F) return;` ——
   它现在会**正确地**把"指针字节"挡掉；
   但注意它**同时会挡掉合法的非 ASCII 文化名**，属**可接受的取舍**
   （配置文件里的文化名本来就是 `[a-z0-9_]`）。
3. **诊断要并排记录两种读法**：`raw_bare`（裸 `+0x48`，复现旧行为）与 `raw_sso`（SSO 判据）
   —— **一次实机即可并排对照**，这比争论有效。

## 4. 一次实机即可定论的判据

打这三样（**同一文化、同一次调用**）：

| # | 打印内容 | 期望 |
|---|---|---|
| 1 | `cu+0x48` 处的 8 字节（hex） | 短名 ⇒ `73 77 65 64 69 73 68 00`（`"swedish\0"`）；<br>长名 ⇒ **看着像指针**（如 `00 3A C2 41 02 00 00 00`） |
| 2 | `cu+0x48+0x18` 的 qword（= cap） | 短名 **15**；长名 **≥ 16** |
| 3 | 按 SSO 判据取出的字符串 | **两种都应是干净的文化名** |

⇒ 若 **3 成立而 1 在长名时是垃圾**，本诊断被实机确证。

## 5. 防御性自检：接手任何对象之前先验证它像不像一个完好的 `CString`

这个坑的另一面是**崩溃**。项目里发生过一次：

```
C0000005 @ RVA 0x94F4A     （CString 移动赋值读源越界）
异常记录里 Rdi = 0x13      ← 有人拿"值等于 19 的假指针"当 CString* 用
```

**崩溃点在被数千处内联调用的通用函数里，回溯不到调用方。**

⇒ 策略改成：**接手任何对象之前，先验证它像不像一个完好的 `CString`，不像就放手。**

```
size ≤ cap、cap ≤ 0x10000、堆串的 data 指针落在用户地址区间
```

三条全部通过才动手；**任何一条不满足就立刻放手**（宁可这个文化顺序不变，也绝不去踩容量边界）。

## 6. 判据代码：怎么系统性地找到所有"裸读"点

1. **找所有 `+0x48`（或任意字符串字段）的直接使用**：
   在 IDB / 源码里搜该偏移的立即数；
2. **对每一处问三个问题**：
   - 这个偏移处的对象是**哪个类**？（vtable → 首参 → 对象大小，见 `docs\01` §3.6）
   - 读到的是**字段起始**还是**字段中间**？（差 0x10 就是 size、差 0x18 就是 cap）
   - 有没有 `cap < 0x10` 的判据？
3. **写一个"安全读取"函数，强制所有路径走它** —— 而不是每处各写一遍。

> ★ 本项目最后就是这么修的：补丁里**已经有**一个带 SSO 判据的 `cc_cstr_field`
> （读 `+0x120` 的 id 串时在用），**修法 = 让那两处裸读也走同一套读法**。

## 7. 这个坑的普适教训

1. **`std::string` 不是 `char*`，永远不是。** 跨模块读别人的字符串字段时，
   第一件事是确认它是不是 SSO 类型。
2. **"测试用例全过"不构成证据。** 短串全过、长串全错，是因为**测试数据的长度没覆盖阈值**。
   ⇒ **测试用例里必须包含长度刚好在阈值两侧的样本**（14 / 15 / 16 / 17 字符）。
3. **"同一串字节涉及多个对象"是强信号。** 不同对象读到相同内容 ⇒
   你读的多半是**指针值**或**共享缓冲区**，不是它们各自的属性。
4. **不要自创读法。** 引擎自己有统一的读取模式（`cmp [x+18h],10h`），**照抄它**。
5. **同一个偏移在不止一个类上都出现过。** 读之前先用 vtable 定类型。
