目标：让**顾问 / 将领 / 外交官 / 共和制统治者**也支持姓前名后（统治者已由双字节补丁支持）。
对象：`eu4.exe` v1.37.5.0 `SHA256 9AD3EFE1…`；双字节补丁 = EU4DLL（`plugins\plugin64.dll`，521,216 字节）。

## 1. 补丁的机制：标记驱动反转（**非**自动判定）

### 1.1 源码依据（x86 旧版，`Plugin/NameOrder.cpp`，对应 issue #98）

```cpp
// name_creation_func_fix_v1283_start
add  esp, 4
cmp  byte ptr [eax+1], 0xBF      // ★ 检查标记
jnz  jmp2
... 用 npos(-1) 调 CString 成员重排 ...
```
源码注释原文：`esiをチェックして逆疑問符¿(0xBF)が最初に来ていれば反転させる`
（检查 esi，若倒问号 `¿`(0xBF) 在最前则反转）。

### 1.2 x86 / x64 一致（本地实测）

`plugins\plugin64.dll` 里 `cmp byte ptr [reg+1], 0BFh` **命中 7 处**：

| 文件偏移 | RVA | 形态 |
|---|---|---|
| 0x0300A9 | 0x030CA9 | 独立一处 |
| 0x035BAA / 0x035BE8 / 0x035C26 / 0x035C64 / 0x035CA2 / 0x035CE3 | 0x0367AA–0x0368E3 | **6 处近似复制**（同一模板的 6 个特化） |

每处前后都是**钩子桩**：
```asm
call qword ptr [rip+X]        ; 原调用（经 .fptable 的游戏函数指针）
push qword ptr [rip+Y]
ret                           ; ← 蹦床，等价 jmp
cmp  byte ptr [rax+1], 0BFh   ; ★ 检查返回的字符串
jnz  skip
mov  qword ptr [rsp+20h], -1  ; -1 = npos ⇒ CString 成员调用
xor  r9d, r9d / mov r8, rax / xor edx, edx / mov rcx, r12 / call [rip+Z]
jmp  done
skip: or r9, -1 / xor r8d, r8d / mov rdx, rax / mov rcx, r12 / call …
```
⇒ **x64 版与 x86 版同源：检测 `0xBF` 标记后反转名字两部分。**

## 2. 数据约定：**引号内紧跟一个裸 `0xBF` 字节**

原始字节证据（`mod\Asian Praefectura Universalis\common\countries\Anqing.txt`）：

```
L326: leader_names = {
L327: "¿1g"   # Zhu     hex: 22 bf 10 31 67 22      ← " + BF + 名字字节 + "
L328: "¿4T"   # Wu      hex: 22 bf 10 34 54 22
L333: "¿Ng"   # Li      hex: 22 bf 10 4e 67 22
L334: "¿òS"   # Shi     hex: 22 bf 10 f2 53 22
```

**关键**：名字是 **UTF-8 中文**，而游戏按 **CP1252 逐字节**读（这正是"双字节补丁"要解决的问题）。
因此在 UTF-8 文本里，`0xBF` 只可能以**续接字节**出现（在中间）；**只有开头的裸 `BF` 是人为标记**。
→ 判据：`"` 之后紧跟 `BF` 即标记（`22 bf`）。

（我最初的假设"标记是 `¿` 字符"在排查中被**证伪**：`common/` 里 583 个含 0xBF 的文件全是
`ï¿½` = U+FFFD；`localisation/` 里 68 个含真 `¿` 的全是**西班牙语**文本。真正的约定是**裸字节前缀**。）

### 7.3 名字的**实际布局**（从用户存档直接读出，E1）

最新存档 `autosave.eu4` 里将领条目的原始字节：

```
general={
    name="öe^ ¿PO PO(g"        ← ★ 拼好的全名 = <名> + 空格 + ¿<姓>
    dynasty="¿PO PO(g"          ← ★ 单独的姓字段，同样带标记
    type=general
    siege=1
    ...
```

**三条结论**：
1. 拼好的 `name` 里标记**紧跟在空格之后** —— 与补丁源码里 `cmp byte ptr [rax+1], 0BFh`
   （`rax` 指向那个空格）**完全对应**，解开了 32 位版注释 `[0]は0x20(white space)` 的疑点。
2. 将领**单独存了 `dynasty` 字段**，且该字段保留标记 ⇒ 名字的两部分在内部是分开的。
3. ⇒ **变换规则**：`name` 中出现 `" ¿"` 时，拆为 `given = 空格前`、`surname = 标记后`，
   重写为 `surname + " " + given`（并剥掉标记）；`dynasty` 字段按需同步剥标记。

### 7.5 挂钩设计（可直接照此实现）

**目标**：`CLeader::SetName` 入口，RVA `0x00861FC0`。

**序言（前 5 字节可安全重放）**：
```asm
0x140861FC0  mov [rsp+arg_10], rbx     ; ★ 5 字节（48 89 5C 24 xx）—— 用 E9 rel32 覆盖
0x140861FC5  mov [rsp+arg_18], rsi     ; ← 回跳点
0x140861FCA  mov [rsp+arg_8], rdx
0x140861FCF  push rdi
0x140861FD0  sub rsp, 30h
0x140861FD4  mov rdi, rdx              ; rdi = a2
0x140861FD7  mov rsi, rcx              ; rsi = this
```
- 入口处 `rdx` = `a2` = **CString\***（第 2 参数），`rcx` = `this`。
- 被覆盖的 `mov [rsp+arg_10], rbx` 是**纯存储、无相对寻址** ⇒ 可在桩中原样重放。
- 回跳地址 = `0x140861FC5`。

**桩逻辑（在 cave 中）**：
```
保存 volatile：rax rcx rdx r8 r9 r10 r11 + flags（pushfq）
rsi_reg = rdx                    ; = CString*
call PatchNameOrder(rsi_reg)     ; 见下
恢复 flags + 寄存器
mov [rsp+arg_10], rbx            ; 重放被覆盖的指令（此时 rsp 与入口一致 ⇒ disp8 仍正确）
jmp 0x140861FC5
```

**`PatchNameOrder(CString* s)`**（纯内存操作，不调用游戏函数）：
```c
unsigned char *base = (unsigned char *)s;
size_t cap  = *(size_t *)(base + 24);
char  *buf  = (cap >= 0x10) ? *(char **)base : (char *)base;   // MSVC SSO 判据 = cap >= 16
size_t size = *(size_t *)(base + 16);
if (size < 3) return;                       // 太短，不可能含 " ¿"
/* 扫描 0x20 0xBF */
size_t p = 0;
for (; p + 1 < size; p++)
    if (buf[p] == 0x20 && (unsigned char)buf[p + 1] == 0xBF) break;
if (p + 1 >= size) return;                  // 未命中 ⇒ 零影响放行
size_t given_len = p;                       // given = buf[0..p-1]
size_t sur_off   = p + 2;                   // surname = buf[p+2 .. size-1]
size_t sur_len   = size - sur_off;
if (sur_len == 0) return;                   // 标记后为空 ⇒ 不动
/* 新串 = surname + " " + given，长度 = size - 1（比原串短 1 字节，无需重分配） */
unsigned char tmp[512];                     // 栈上暂存；名字长度有界
if (sur_len + 1 + given_len >= sizeof(tmp)) return;
memcpy(tmp, buf + sur_off, sur_len);
tmp[sur_len] = ' ';
memcpy(tmp + sur_len + 1, buf, given_len);
memcpy(buf, tmp, size - 1);
buf[size - 1] = 0;
*(size_t *)(base + 16) = size - 1;          // 更新 size
```
- **长度只减不增**（去掉 1 字节标记）⇒ 无论 SSO 还是堆缓冲都能就地改写，**不需分配、不需调用
  `StringAssign`** ⇒ 桩可保持"纯内存操作"，符合规范里 `DllMain`/cave 的安全约束。
- 未命中标记时**一个字节都不改** ⇒ 对未标记的存档/数据零影响。

### 7.5b **存储层差异 —— 补丁对将领无效的根本原因**（存档实证，E1）

对比存档里**君主**与**将领**的字段形态：

```

heir={      name="V÷·ÌKQ"   ...   dynasty="¯Q ôuyrS¯eôTk"  ← ★ 同样分开
```

| 存档结构 | `name`（名）与 `dynasty`（王朝）**分开两个字段** | `name` 是**已拼好的单个串**（顾问无 dynasty 字段） |

**这解释了你的观察，也决定了实现路线**：将领/顾问的拼装发生在创建时（`CLeader::SetName`），
显示端不再拼装 ⇒ 只在拼装层修，则**已存在于存档里的角色不会被修**；
要做到"新旧都修"，需要在**读取/显示层**做变换，与统治者路径的分层方式保持一致。

**已排除**：`CLeader+0x20`（姓名字段）**没有简单的内联 getter** ——
在全 `.text` 里搜 `lea rax,[rcx+20h]; ret` / `mov rax,rcx; add rax,20h; ret` 只得 4 处无关小函数。
⇒ 显示端是直接读字段（或经更复杂的访问器），需另找挂点。

**结论（本轮的设计定论）**：
1. **将领**：`CLeader::SetName`（`0x140861FC0`）是创建路径的理想单点；若还要修旧存档，
   需再挂**存档读取**或**显示**层。

   且全 exe 只有一条 `SetName` 日志 ⇒ 其写入点尚未定位。
3. 变换逻辑本身已实现并**单测通过**（见 §7.7）。

### 7.5d **落点定论：挂在共享拼装函数 `BuildFullName_Impl` 的唯一出口**（本轮最终方案）

**为什么是它**：顾问的名字来源已查明 —— `advisor.cpp` 的 `Advisor_Init` 调用
**`GenerateMonarchName`（`0x140313D90`）**，与君主**同一个函数**；而 `GenerateMonarchName` 尾部
唯一调用 `BuildFullName_Impl`（`0x140313F40`）。将领侧 `create_general` 也在 `0x140649BE8`
调用 `GenerateMonarchName`。⇒ **三者的拼装都汇聚到 `BuildFullName_Impl`**。

**为什么补丁漏了顾问/将领**：双字节补丁是**挂钩调用点**（plugin64.dll 里 6 个近似复制的
钩子桩），只覆盖了君主的那几个调用者；顾问/将领的调用点没被覆盖 ⇒ 文本里留下 `¿` 且顺序未反转。

**为什么挂在这里安全**：变换会**消耗掉 `0xBF` 标记**。已被补丁处理过的君主路径在到达
`BuildFullName_Impl` 出口时标记已不存在 ⇒ 我们的变换自动 no-op，**不会二次反转**。
（顺序依赖性成立，但结论稳健：两条路径最终都只剩一个带标记的形态。）

**函数结构**（RVA `0x313F40`–`0x31434F`，`0x40F` 字节）：

| 关键点 | RVA | 说明 |
|---|---|---|
| `StringAppend` ×3 | `0x31425B` / `0x314272` / `0x3142F7` | 拼装（其中一个注入空格） |
| `DynastyStore_Find` | `0x3142CD` | 取**带标记的姓**（夹在两次 append 之间） |
| `mov rax, rdi` | `0x31432B` | `rax` = 返回值 = 结果 `CString*` |
| `pop r15 / pop r14 / pop rbp` | `0x314349` / `0x31434B` / `0x31434D` | **恰好 5 字节**：`41 5F 41 5E 5D` |
| `retn` | `0x31434E` | **全函数唯一出口** ✓ |

**桩设计（5 字节站点 = 3 个 pop，回跳 `0x31434E`）**：

```asm
; 进入时：rax = 结果 CString*，rsp ≡ 8 (mod 16)
sub  rsp, 0x228            ; 0x228 mod 16 = 8 ⇒ rsp 变为 ≡ 0，满足 call 前的 ABI 对齐
mov  [rsp+0x200], rax      ; 保存返回值（call 会破坏 volatile 寄存器）
mov  rcx, rax              ; 参数 = 结果 CString*
mov  rax, <MyTransformVA>  ; 我方 C 函数的绝对地址（打补丁时写入）
call rax                   ; ★ 纯内存操作，不调用任何游戏函数
mov  rax, [rsp+0x200]      ; 恢复返回值
add  rsp, 0x228            ; 还原 rsp
pop  r15                   ; ← 重放被覆盖的 3 条指令
pop  r14
pop  rbp
jmp  0x14031434E           ; 回到 retn
```

- **为什么能保存返回值**：`rax` 在 `0x31432B` 已设好且不被 3 个 pop 触碰 ⇒ 出口处即结果指针。
- **对齐核算**：入口 `rsp ≡ 8 (mod 16)`（`call` 压入返回地址）；`sub rsp,0x228`（552 ≡ 8 mod 16）
  ⇒ 到 `call` 时 `rsp ≡ 0` ✓ 满足 MSVC x64 的 `call` 前对齐要求。
- **栈安全性**：保存的 `r15/r14/rbp` 在更高地址处，`sub rsp` 向下开辟 ⇒ 不触碰它们 ✓
- 变换函数即已通过 12/12 单测的 `patch_name_order`（`src\monarchnamefix\nameordertest.c`）✓

**覆盖面**：君主（若补丁未处理）、**顾问**、**将领**一并解决；且**存档里的旧角色也会被修**——
前提是 `BuildFullName_Impl` 在**存档读取**时也参与显示名的组装（需在实机/静态上确认一次）。

**仍需收口**：
1. **外交官与共和制统治者**：需先确认"外交官"在这款游戏里指哪个对象（EU4 的外交官/使节可能是
   无名资源计数），以及共和制统治者是否走 `BuildFullName_Impl`（其头衔走政体属性槽 5
   `republican_name`，姓名本体应仍走此函数）。

### 7.10 覆盖面反查（第 8 轮）：**不存在绕过 P4/P5 的第三条拼装路径**

做法：把所有"取带标记姓氏"的调用点（`DynastyStore_Find` / `ResolveDynastyFromCharacter` /

| 函数 | 有无拼接动作 | 结论 |

| `sub_1402C2B10` | 无 —— 解析王朝后转交 `Country_CreateHeir_Impl` | 拼装在 `Country_CreateNewMonarch`/`BuildFullName_Impl` ⇒ **P4** |

### 7.12 **实机暴露的安装层缺陷（P4/P5 装不上）与其根因** —— 教训记录

实机日志（用户提供）：
```
[i] ready P1 … site=0xda989b     [i] ready P2 … site=0x280274     [i] ready P3 … site=0xda9a82
[!] original bytes mismatch: P4 BuildFullName_Impl exit (name order)
[!] original bytes mismatch: P5 CLeader::SetName entry (name order)
[i] result: 3/5 patches applied
```

**两个缺陷（都在 `prepare_one` / 补丁表，不在桩也不在变换）**：

**① 护栏用"签名前 5 字节"比对站点。**
```c
for (i = 0; i < 5; i++)
    if (!s.mask[i] || site[i] != s.bytes[i]) { 失败 }   // ← 错
```
`!s.mask[i]` 意为"该字节是 `??` 通配"，却直接判失败 ⇒ **签名里只要带通配就必然不通过**。
P1–P3 的签名前 5 字节恰好全是具体值，所以侥幸成功；P4/P5 的签名第 5 字节是 `??` ⇒ 必失败。

**② `site` 直接取签名命中处，而 P4 的站点不在那里。**
```c
site = (uint8_t *)hit;   // hit = 签名命中处 = BuildFullName_Impl 开头 0x00313F40
```
P4 要打的站点是**函数唯一出口** `0x00314349`（尾部 3 个 `pop`）。
`rva` 字段被用作"签名命中处的交叉校验值"，于是站点被当成函数开头 ——
**即使护栏放行，P4 也会去改写函数序言**，后果严重。

**修法**：把两个概念拆开
- `rva` = 签名命中处的预期 RVA（交叉校验"是不是同一个函数"）
- **`site_rva`** = 真正打补丁的站点 RVA（P1–P3 与 `rva` 相同；P4 不同）
- **`site_bytes`** = 站点原字节（hex + `??` 通配），护栏按它逐字节校验

**③ 为什么离线没拦住 —— 校验器的升级（本轮补上）**

此前 `verify_nameorder_target.py` 只**手工**查了 P4 一个站点的字节，没有校验"安装逻辑"。
现改为**从 `monarchnamefix.c` 解析整张补丁表**，逐条对 eu4.exe 校验：
签名命中 RVA、`site_rva` 处原字节、回跳点位置（出口型站点须为 `C3`）与 `cover >= 5`。

```
P1 … 0xda989b  0xda989b  OK      P4 … 0x313f40  0x314349  OK
P2 … 0x280274  0x280274  OK      P5 … 0x861fc0  0x861fc0  OK
P3 … 0xda9a82  0xda9a82  OK
[PASS] 补丁表全部条目通过静态校验
```

**教训**：桩的机器码我逐一字节核对、还用真实执行测了，却漏掉"**桩挂到哪**"这一层。
以后新增补丁点，必须让校验器覆盖"签名命中处 / 站点 / 回跳点"三者的关系，
而不是只验桩或只验单个站点字节。

**新产物**：`dist\MonarchNameFix.dll`，114,176 字节，
SHA256 `EA71C52AC03DBF1AC2425F8FFD98B50A60E4322E75DD8387F816CBF352D41153`。

### 7.14 **「按文化决定姓前名后」可行性验证：成立**（第 10 轮）

用户要按**文化**（而非 `0xBF` 标记）决定是否姓前名后。核心问题是：**在姓名合成点能否拿到文化？**
结论：**能，且在我现有的 P4 挂钩点上免费可得。**

**证据链（两个独立见证）**

见证一 —— `PickNameFromCulture`(`0x140280340`)：
```c
__int64 PickNameFromCulture(_QWORD *a1, char a2/*性别*/, int a3/*随机*/)
{
  v3 = a1[17];                                    // a1 + 0x88 = 文化对象
  if (a2) return PickNameFromCultureLists(a1, a2, a3, a1 + 25, (v3 + 224));  // 文化+0xE0 男名表
  else    return PickNameFromCultureLists(a1, 0,  a3, a1 + 22, (v3 + 200));  // 文化+0xC8 女名表
}
```

见证二 —— `BuildFullName_Impl`(`0x140313F40`) 内部：
```asm
0x140313F68  mov r14, r8            ; ★ 第 3 个参数 (r8) → r14
0x1403141A4  mov rax, [r14+88h]     ; ★ 文化对象 = *(第3参数 + 0x88)
0x1403141B0  lea rcx, [rax+0E0h]    ; 男性：文化对象 + 0xE0
0x1403141C9  add rax, 0C8h          ; 女性：文化对象 + 0xC8
0x1403141DD  call PickNameFromCultureLists
```
两处都从同一偏移（`+0x88`）取对象、再取 `+0xC8`/`+0xE0` 的男女名表 ⇒ 该对象**确凿是「文化」**
（不是国家、不是宗教）。

**为什么 P4 挂钩点能直接用它**：函数序言 `push r14`，尾声为
`pop r15 ; pop r14 ; pop rbp`（正是 P4 覆盖的 5 字节站点）。
我的桩在**这三个 pop 执行之前**进入 ⇒ **`r14` 仍等于第 3 参数** ⇒ 一条
`mov rax, [r14+88h]` 即得文化对象 ✓✓

**结论**：把 P4 的判据从"检测 `0xBF` 标记"换成"查 `*(r14+0x88)` 这个文化是否在配置的名单里"，
即可实现按文化一刀切，且**不需要改变桩的挂点、不需要新的桩**。

**剩余待办（实现前需定）**
1. **配置的键怎么定**：文化对象的**名字/ID 字段**尚未定位。两条路——
   (a) 找到文化对象的名称字段（可与配置文件里的文化名比对）；
   (b) 初始化时把配置里的文化名解析成对象指针，运行时只比指针。
2. **P5（`CLeader_SetName` 入口）拿不到文化** —— 它的入参只有 `this` 与姓名字符串。
   但将领名有**两条**路径：经 `BuildFullName_Impl` 的走 P4 ✓；**内联拼装**那条
   （`create_general` 的 `0x140649A87/AA7`）需另找文化来源。可行落点：
   该路径上 `PickNameFromCulture` 的调用点 `0x140649997`，其 `rcx` 即承载文化的结构
   （同样按 `+0x88` 取）✓
3. 顾问/外交官（`envoy` 的四类）names 全走 `GenerateMonarchName` → `BuildFullName_Impl` ⇒ **只需 P4** ✓
