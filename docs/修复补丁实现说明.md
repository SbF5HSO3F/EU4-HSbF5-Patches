# MonarchNameFix 修复补丁 — 实现说明

目标：`eu4.exe` v1.37.5.0 Inca (491d)
SHA256 `9AD3EFE1AF169F40EE577F9DAE5DEBBC87AF6FB8B5450FB345EBF110DC4D771A`

缺陷：加权表选取器用**有符号取模**（`cdq; idiv`）处理带符号位的 32 位随机值，
负余数使线性权重扫描第一步即 `break`，恒返回该组**第一个条目**
⇒ 「名字库第一号位被选中概率被严重放大」。（分析见 `继承人与随机姓名-逆向分析.md`）

**本实现不引入任何第三方代码**：PE 解析、签名扫描、cave 分配、字节改写、桩机器码全部自写。

## 2. 补丁点（最终形态：只有 3 个跳板）

关键简化：**不必逐个修那 6 处 `idiv`**。随机值有两个使用路径 ——
mode1 直接读 `edx`，mode0/mode2 读 `esi`（由序言的 `mov esi,edx` 搬入）。
在序言处把 `edx` 与 `esi` 同时掩为非负，**一处改动即覆盖全部 3 个 mode**。

| # | 位置 | RVA | 覆盖 | 回跳 RVA | 桩长 | 作用 |
|---|---|---|---|---|---|---|
| P1 | `WeightedNameList_PickByRandomIndex` 序言 | `0x00DA989B` | 5 | `0x00DA98A0` | 16 | 掩 `edx` + `esi` → 修 mode 0/1/2 |
| P2 | `PickNameFromCultureLists` 取模 | `0x00280274` | 5 | `0x0028027A` | 17 | 文化名回退的无符号取模 |
| P3 | `WeightedNameList_GetByModIndex` 取模 | `0x00DA9A82` | 5 | `0x00DA9A88` | 17 | 40 字节元素表的无符号取模 |

### P1 桩（16 字节）

```asm
49 8B F8              mov  rdi, r8          ; 重放被覆盖的原指令
81 E2 FF FF 1F 00     and  edx, 001FFFFFh   ; ★ 掩为 [0, 2^21)
8B F2                 mov  esi, edx         ; mode0/2 用的副本同样已掩
E9 <rel32>            jmp  0x140DA98A0      ; 回到 mov r10,rcx / cmp eax,1
```

被覆盖的原指令是 `mov rdi,r8` 与 `mov esi,edx`（共 5 字节），桩把它们**重放**后多做了掩码。

### P2 / P3 桩（各 17 字节）

```asm
8B C7 / 8B C2         mov  eax, edi / edx   ; 重放
25 FF FF 1F 00        and  eax, 001FFFFFh
31 D2                 xor  edx, edx
41 F7 F0              div  r8d              ; ★ 无符号除法，余数必落 [0, divisor)
E9 <rel32>            jmp  resume           ; P2→cmp edx,ecx ; P3→lea rax,[rdx+rdx*4]
```

原指令为 `cdq; idiv r8d`（有符号）。覆盖 5 字节后残留 1 字节（`F8`）成为**死字节**，
因为桩回跳到其后一条指令边界，死字节不会被取指。

### 为什么掩码是 21 位

- **消除负余数**：掩后必非负。
- **消除 mode2 的 32 位溢出**：mode2 的被除数是 `1000 * rnd`；
  `1000 × (2^21-1) = 2,097,151,000 < 2^31 = 2,147,483,648` ⇒ 不溢出。
  因此 **mode2 无需另做 64 位重写**。
- **消除 `#DE` 风险**：被除数 < 2^21，任何 `divisor ≥ 1` 的商都 < 2^31，不会除法溢出。
- **分布质量**：`2^21 / 权重和`。实测全 979 个国家文件的 `monarch_names`
  权重和范围为 **18 – 2340** ⇒ 比值 ≥ 896 ⇒ 取模偏差 **< 0.12%**，可忽略。

## 3. 护栏（全部实现于代码内）

1. **宿主校验**：主模块文件名必须是 `eu4.exe`，否则直接返回、一字不改。
2. **构建指纹**：`SizeOfImage == 0x025E0000` 且 `TimeDateStamp == 1727949497`，
   任一不符即**放弃全部补丁**并写日志。
3. **签名定位**（非硬编码地址）：在首个可执行节内做带 `??` 通配的特征扫描。
4. **RVA 交叉校验**：命中位置必须等于预期 RVA，否则放弃该补丁。
5. **原字节校验**：写入前二次确认站点首 5 字节，不符即放弃。
6. **逐补丁独立**：单个补丁失败不影响其余；失败一律**不改写**。
7. **跳转位移边界检查**：site→stub 与 stub→resume 的 `rel32` 都做范围校验，越界即放弃。
8. **可关闭**：`plugins\MonarchNameFix.off` 存在时完全不动作。
9. **可观测**：结果写 `plugins\MonarchNameFix.log`（含指纹、cave、每个补丁的成败与地址）。
10. **最小加载足迹**：`/MT` 静态 CRT ⇒ 只依赖 `KERNEL32.dll`；
    日志只用 `CreateFileW/WriteFile`，**不在 loader lock 下加载任何新库**。

## 6. 尚未覆盖 / 待实机确认

1. **未做真实游戏内动态验证**：本机沙箱内无法启动游戏，
   故 4.1/4.2 是静态与单元级验证，**统计级验证需你实机跑一次**
   （反复触发继承人诞生，观察姓名分布是否不再集中）。
2. **残留的潜在缺陷（本次未改）**：
   - `BuildFullName_Impl`（`0x140313F40`）对 `WeightedNameList_GetByModIndex` 的返回值
     **未判空**即解引用 `*(v15+36)`；空表时 `WeightedNameList_GetByModIndex` 返回 0 → 读地址 `0x24`。
     属独立缺陷，改动需确认预期语义，故未纳入本补丁。
   - `Random_GetGlobalMT` 在 `byte_141FD10C4`（forbidden area）置位时返回 0，
     同样会使索引恒为 0；当前证据显示非 `Heir_InitNewHeir` 的正常路径。
3. **影响面**：mode 0/1 的遍历被条目 `+36` 过滤，返回条目必属该组、组内 `+36` 相同，
   ⇒ **性别不变，只有名字变**。mode 2（两组混合）下性别可能改变。
   联机场景与未打补丁的玩家校验和不一致。

## 7. 实机故障与修复记录（2026-10-02，首轮实机反馈）

### 7.1 现象

实机运行后日志只有三项，**没有 `[i] result:` 行，也没有任何 `[!]` 失败行**：

```
=== MonarchNameFix (build Oct  2 2026 21:09:47) ===
[i] image size=0x25e0000 timestamp=1727949497
[i] fingerprint ok
[i] cave=0xffff0000 slot=32
[+] patched P1 WeightedTable_PickByRandomIndex entry site=0xda989b stub=0xffff0000
```

而**游戏正常运行，且用户确认姓名分布已不再集中在第一号位**。

### 7.2 根因（已验证）

`apply_one` 里唯一"静默终止"的位置就是写桩字节那一行。原因是**保护位顺序错误**：

```c
/* P1 */
for (i = 0; i < 16; i++) cave[i] = stub[i];        /* 此时 cave 仍是 VirtualAlloc 给的 RWX */
VirtualProtect(cave, 16, PAGE_EXECUTE_READ, &old); /* ★ 影响的是【整页】而不是那 16 字节 */
...
/* P2：槽位在 cave+32，同一页 —— 此时该页已只读 */
for (i = 0; i < 17; i++) cave[i] = stub[i];        /* ★ 访问违例 */
```

异常从我们的 `DllMain` 逃出 → 加载器判定该 DLL 加载失败（**静默**，不弹窗、无日志）
→ 后续 P2/P3 未执行。
但 **P1 的站点补丁在此之前已经写进 `eu4.exe` 的内存**，所以功能照旧生效 ——
这正好解释了"游戏正常 + 补丁部分生效 + 日志截断"三者同时出现。

**证据**：`stubtest.c` 新增回归用例，在同一页上复现该序列：

```
[regress] write to same page after VirtualProtect(RX): FAULT
          -> confirmed: all stubs must be written BEFORE protecting
```

> 附带说明：日志里的 `cave=0xffff0000` 是**日志格式化缺陷**，不是地址异常。
> `cave` 实际在模块基址**下方** 64KB（`alloc_near` 从 `base - 64KB` 开始试），
> 而 `cave - mod` 为负、按 `uint32` 打印就成了 `0xffff0000`。

### 7.3 修复

**改为两阶段安装**（`prepare_one` / `hook_one`）：

| 阶段 | 动作 | 此时 cave 权限 |
|---|---|---|
| 1 | 对**全部**补丁：签名定位 → RVA 交叉校验 → 原字节校验 → 写桩 + 填桩尾 jmp | RWX（可写） |
| 2 | **一次性** `VirtualProtect(cave, cave_need, PAGE_EXECUTE_READ)` + `FlushInstructionCache` | → RX |
| 3 | 才去逐个把站点改成 `jmp rel32` | RX |

另外两项加固：

1. **SEH 兜底**：三阶段整体包在 `__try/__except` 内，任何意外异常都会写入
   `[!] unexpected exception, code=0x...` —— 避免再次出现"静默失败"。
   （已确认加固后产物仍为 **0 导出 + 仅导入 `KERNEL32.dll`**。）
2. **cave 地址日志改为绝对地址 + 带符号偏移**（`+NNNN (above base)` / `-NNNN (below base)`），
   不再出现误导性的 `0xffff0000`。

### 7.5 重要说明：为什么"只挂上 P1"也能改善现象

P1 修的是 `WeightedNameList_PickByRandomIndex` 的**入口掩码**，而该函数正是
`monarch_names`（统治者/继承人名字）的选取器 —— **主症状就由它决定**，
所以 P1 单独生效即可让分布正常。

P2/P3 分别修 `PickNameFromCultureLists`（**仅在加权表未命中时的回退路径**）
与 `WeightedNameList_GetByModIndex`（40 字节元素表）。它们属于**残留缺陷**：
先前因为 P1 的缺陷使加权表几乎总能命中，回退路径很少被走到；
P1 修好之后回退路径调用频率会上升，**P2 那个越界读反而更容易被触发** ——
所以这两处必须一并挂上，建议更新到新版本后复查日志是否为 `3/3`。
